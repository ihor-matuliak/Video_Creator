# Архітектурні рішення

## ADR 001 Локальний desktop

Windows 11 x64, Electron/React/TypeScript + Python FastAPI sidecar, SQLite, FFmpeg. Причина: native paths для великих файлів, зручний review UI, reuse Python media/AI ecosystem. Наслідок: два runtime і окремий packaging gate; перевірити sidecar bundle у M0. macOS/Linux не входять у перший release gate.

## ADR 002 Текстовий відбір

MVP використовує транскрипцію та ручну перевірку картинки. Причина: погоджений фокус — нарізання, STT і категорії. Наслідок: silent visual events можуть бути пропущені; UI і benchmark розділяють їх. Video understanding — окреме майбутнє розширення.

## ADR 003 Тести перед реалізацією

Пакет містить black-box HTTP/UI tests, які фіксують public behavior. Вони доповнюються unit/integration під час написання коду. Невиконані продуктні тести позначаються NOT RUN, а перевірки пакета — окремо.

## ADR 004 Точність часу

Integer milliseconds, source-relative canonical origin, [start,end). Word/segment IDs є evidence і не замінюються вигаданими LLM часами. FFmpeg policies приймаються після content-boundary tests, а не за синтаксично правдоподібною командою.

## ADR 005 Платні запити

Default tests offline. Live вмикається явно з API-key і ceiling. Unknown paid timeout не повторюється автоматично. Причина: локальний клієнт не може гарантувати exactly-once billing у стороннього сервісу.

## ADR 006 Toolchain Python (2026-11-13)

Python 3.12 (3.12.16), встановлений через uv у профіль користувача; системний Python 3.14 не використовується. Єдиний менеджер залежностей і lock tool для backend — uv (uv.lock). Node 24.12.0, FFmpeg 8.1 gyan.dev full build.

## ADR 007 STT за замовчуванням (2026-11-13)

Власник обрав microsoft/mai-transcribe-2 основною STT-моделлю. Адаптер google/gemini-3.5-transcribe лишається за FR-013 (P0) як перемикний, але не default. Модель аналізу ще не обрана: визначається в M0 п.6 / M4 після capability probe. Ключі OpenRouter власник надає на запит у момент live-перевірки; до того — fake provider, live gates NOT RUN.

## ADR 008 Пакування і ліцензія FFmpeg (2026-11-13)

Програма лише для особистого використання власником, без поширення; GPL-збірка FFmpeg (libx264) допустима, ліцензії все одно включаються в inventory. Packaged-перевірку M8 виконуємо на ПК власника (per-user installer без прав адміністратора). Цей ПК має dev Python/Node, тому T-056 «чиста Windows» на ньому не доводиться і звітується як NOT RUN, якщо не буде окремої VM.

## ADR 013 Контракт запуску sidecar (2026-11-13, M0)

`python -m clipforge.server --port N [--config-stdin]`, cwd apps/backend.
- `--port 0` — ефемерний порт; після bind sidecar друкує один рядок stdout `{"event":"ready","port":N}`. Main не вгадує вільний порт (немає race).
- `--config-stdin` — перший рядок stdin: JSON `{"mode":"production"|"test","data_dir":"...","session_token":"..."}`. Після цього sidecar стежить за stdin і завершується на EOF (смерть батька не лишає сироти).
- Без `--config-stdin` конфігурація з env (§6 у 04_ARCHITECTURE_API) дозволена лише при CLIPFORGE_MODE=test. Production відхиляє CLIPFORGE_MODE=test, будь-які CLIPFORGE_TEST_* і не-loopback provider URL; test provider URL лише http://127.0.0.1|localhost.
- Bind лише 127.0.0.1. Bearer на всіх маршрутах (constant-time порівняння); 401 і чужий Host — до читання даних; помилки у форматі §4 з українським message; 500 без тексту винятку; токен ніколи не логуються (access log вимкнено).

## ADR 014 Test mode у desktop (2026-11-13, M0)

Electron main вмикає test mode лише якщо env CLIPFORGE_E2E=1 або CLIPFORGE_MODE=test; тоді передає sidecar `mode:"test"` і data dir із CLIPFORGE_DATA_DIR, а renderer показує бейдж «Тестові дані». Інакше production і data dir у app.getPath('userData'). Пакування (M8) має прибрати цей шлях або підтвердити, що він не активується випадково.

Уточнення до ADR 013 після реалізації (M0): чужий Host → 400 `INVALID_HOST`; перевірка Host іде до токена (дозволено лише `127.0.0.1:<port>` і `localhost:<port>`). Auth і Host — чистий ASGI middleware до роутингу, тому й невідомий маршрут без токена дає 401. 404/405/422/500 теж у форматі §4; 422 містить лише `loc`/`type` без значень запиту; docs/redoc/openapi вимкнені. Stdin-конфіг має строгий набір ключів, `data_dir` абсолютний, токен ≥32 друкованих ASCII. Ready-рядок друкується після старту uvicorn на заздалегідь прив'язаному сокеті 127.0.0.1.

## ADR 016 Дрібні рішення desktop M0 (2026-11-13)

- Preload відкриває `window.clipforge = {bridgeVersion: 1, getStatus}`. `bridgeVersion` — заморожена константа для сумісності мосту, не можливість; токен, fetch і Node API renderer не отримує (перевіряє E2E smoke).
- CSP у `electron-vite dev` (лише serve) послаблено до `'unsafe-inline'` для скрипта React Refresh і `ws:` для HMR. Зібраний/пакований renderer має строгий `default-src 'self'` (перевіряє Vitest-тест index.html); з M2 T4 додано лише `media-src app-media:` для програвача (ADR 022). Packaged build не використовує dev-сервер. Уточнення 2026-11-15: послаблення будує `src/main/dev-server-csp.ts` зі строгої політики index.html. Усі строгі директиви лишаються, додаються лише `script-src`/`style-src 'self' 'unsafe-inline'` і `connect-src` для ws. Якщо політика має несподівану форму, плагін кидає помилку і нічого мовчки не пропускає (тест dev-server-csp.test.ts).
- Додаткові dev-pins поза ADR 011 (точні, без ^/~): @eslint/js 10.0.1, eslint-plugin-react-hooks 7.1.1, globals 17.14.0, @testing-library/dom 10.4.2, @testing-library/jest-dom 7.0.1, @types/node 24.19.2, @types/react 19.3.0, @types/react-dom 19.3.0, jsdom 29.1.1.

Уточнення до ADR 013 (M0, після рев'ю): необроблений виняток перехоплює зовнішній ASGI `UnexpectedErrorMiddleware`; у лог іде лише `Unhandled <ClassName> (error_id=<16 hex>)` без тексту винятку і traceback, відповідь 500 у форматі §4 має `details.error_id` для зіставлення з логом. Регресійний тест — apps/backend/tests/test_server_unexpected_error.py (реальний uvicorn у підпроцесі).

## ADR 017 Каркас ядра M1 (2026-11-13)

- Шари backend за docs/04 §2: `clipforge/domain` (чисті функції: timecode, interval, naming, catalog), `clipforge/storage` (SQLAlchemy 2.1 + Alembic), `clipforge/adapters` (процеси, ffprobe, ffmpeg, fingerprint), `clipforge/services` (оркестрація, export, jobs). Domain не імпортує FastAPI/SQLAlchemy.
- SQLite: `<data_dir>/clipforge.sqlite3`, WAL, `foreign_keys=ON`, busy_timeout; міграції Alembic запускаються програмно під час старту; перед upgrade наявної БД — копія в `<data_dir>/backups/`; при невдалій міграції sidecar завершується з кодом 2, попередня схема лишається. Workspace lock `<data_dir>/workspace.lock` (msvcrt) на весь час процесу: другий sidecar на той самий data dir не стартує. ID — uuid4-рядки; час журналів — ISO 8601 UTC; JSON-поля мають `schema_version`.
- FFmpeg/FFprobe: шляхи визначаються один раз під час старту — у test mode з `CLIPFORGE_FFMPEG_PATH`/`CLIPFORGE_FFPROBE_PATH`, інакше `shutil.which` → абсолютний шлях; версії записуються в manifest. Немає інструментів → media-маршрути повертають 503 `MEDIA_TOOLS_UNAVAILABLE`, health працює. У M8 Electron передасть шляхи бандла через stdin-конфіг.
- Jobs у M1: рядки Job у БД + потоки-воркери в процесі sidecar (export — 1, SHA-256 — 1). На старті `queued`/`running`/`cancelling` → `interrupted` (уточнено 2026-11-14, див. ADR 019). Leases/resume — M6.
- Рецепт exact cut (порядок seek/trim/setpts) фіксується окремим ADR після spike і тестів T-003/T-008/T-009.

## ADR 018 Рецепт exact cut (2026-11-13, M1 spike)

Spike на копіях фікстур (FFmpeg 8.1). S/E — секунди від нуля контейнера: canonical origin + ms/1000; filtergraph будується лише з чисел, відформатованих кодом.

```
ffmpeg -ss <max(0,S-3)> -copyts -i <src>
  -filter_complex "[0:v:0]trim=start=S:end=E,setpts=PTS-S/TB[v];
                   [0:<aidx>]atrim=start=S:end=E,asetpts=PTS-S/TB,aresample=async=1:first_pts=0[a]"
  -map [v] -map [a] -c:v libx264 -crf 18 -preset medium -pix_fmt yuv420p -bf 0
  -fps_mode passthrough -enc_time_base:v demux -c:a aac -b:a 192k <tmp>.mp4
```

- `-copyts` + trim/atrim за абсолютним часом дає межі за фактичними PTS (non-keyframe start: перший кадр зелений, PTS 0,013; VFR: інтервали 0,033 і 0,067 збережені).
- `aresample=async=1:first_pts=0` заповнює тишею пізній старт аудіо (audio_offset: тиша до 1,000 с, rms 0,0 / 0,088), а не лише зсуває контейнер.
- `-enc_time_base:v demux` — без нього x264 квантує PTS до 1/fps. `-bf 0` для всіх експортів: з B-кадрами MP4 edit list обрізає останній VFR-кадр і duration виходить 2,9 замість ~2,97 с; `+negative_cts_offsets`/`-use_editlist 0` не допомагають. Ціна — трохи більший файл за того ж CRF. Тривалість останнього VFR-кадру береться з default frame interval.
- Pre-seek (`-ss S-3` до `-i`) безпечний лише для форматів з індексом (mov/mp4, matroska). На MPEG-TS seek перескакує на наступний keyframe після цілі (GOP 10 с → вихід порожній). Тому: pre-seek лише для mov/mp4/matroska; для решти — декодування від початку; якщо перевірка показує порожній вихід або перший кадр пізніше за допуск після pre-seek — один повтор без pre-seek. `seek_mode` (`preseek`/`full_decode`) записується в manifest.
- Без аудіо або `audio=none` — лише `[v]`. Rotation/odd dimensions/HDR — окремими кроками експорту за docs/05 §2 (HDR → unsupported).
- Уточнення (2026-11-14, T4): значення input `-ss` FFmpeg відраховує від `start_time` контейнера (додає його сам), тому pre-seek — `-ss max(0, start_ms-3000)/1000` **без** origin; trim/atrim лишаються в абсолютному часі (origin + ms/1000) завдяки `-copyts`. Варіант `-ss S-3` з origin на джерелі з початком 10 с перескакує ціль. Регресія: `test_nonzero_origin_with_preseek[mkv|mp4]` (зсув 10 с, preseek, усі кадри зелені).

## ADR 019 Дрібні рішення domain і storage M1 (2026-11-13)

- Ім'я експорту: `<stem>_<clip_id>_r<revision>_<HHhMMmSSsmmm>-<HHhMMmSSsmmm>.mp4` (двокрапка в Windows заборонена), повний clip_id, NFC, `<>:"/\|?*` і символи категорій C* → `_`, зарезервовані імена отримують префікс `_`, ліміт 150 UTF-16 одиниць (скорочується лише stem), колізії — суфікс ` (N)`. `first_free_name` лише пропонує ім'я: фіналізація створює/перейменовує без перезапису.
- CSV-каталог: категорії через `", "`, CRLF, текстові клітинки, що починаються з `= + - @ \t \r \n` (зокрема повноширинних або після пробілів), отримують префікс `'`; самотні сурогати → `?`.
- Міграція Alembic — одна транзакція (`transactional_ddl`), невдала ревізія лишає попередню схему й `alembic_version`; БД з таблицями без версії або з новішою невідомою версією не чіпається (`MigrationError`, без бекапу; уточнено 2026-11-14: і journal mode теж — `PRAGMA journal_mode=WAL` виконується лише після успішної міграції, а не в connect-hook). Бекап — `sqlite3.backup` + `integrity_check` у `backups/clipforge-<UTC>-from-<rev>.sqlite3`.
- `Database.session()` — deferred BEGIN, `write_session()` — `BEGIN IMMEDIATE`. JSON-поля зберігаються як `{"schema_version":1,"value":...}`.
- `ClipRepository.update` змінює лише title, start_ms, end_ms, categories, review_status, visual_review_required; review теж збільшує revision; `set_export_state` revision не збільшує, щоб завершення експорту не робило правку користувача застарілою. Позначка verified→stale при зміні меж (FR-032) — у сервісі.
- `Source.mtime` — `st_mtime_ns`; `canonical_origin` — JSON `{origin_ms,time_base}`; CHECK лише для перелічених у docs наборів (review_status, export_state, job.state); `UNIQUE(batch_id, clip_id)` у export_items — дедуплікація з docs/04 §5. `clips.analysis_run_id` — FK на analysis_runs з r0007 (M4, ADR 041 §8).
- Рестарт (уточнено 2026-11-14 за рев'ю M1): `JobRepository.interrupt_unfinished()` переводить `queued`, `running` і `cancelling` → `interrupted`, бо в M1 job живе лише в пам'яті процесу й після рестарту воркера в неї немає. Стан власників відновлюється окремо: hash job створюється заново, export batch закриває `ExportService.recover()`. Leases і resume — M6.
- SRT кліпу (`domain/subtitles.py`, FR-043): cue зсуваються до нуля кліпу й обрізаються межами; сегмент, що перетинає межу, зберігає весь текст (без word timing розбити неможливо); теги/коментарі видаляються до стабілізації, переводи рядків і табуляції → один пробіл, нумерація з 1 за часом.

## ADR 020 API джерел, кліпів і export batches M1 (2026-11-14)

- Старт sidecar: `open_database` → помилка міграції/блокування workspace/OSError → stderr і код виходу 2 без ready-рядка. Немає FFmpeg/FFprobe → `media_tools=None`, `/v1/health` 200, медійні маршрути 503 MEDIA_TOOLS_UNAVAILABLE.
- `Source.hash_status`: pending/computed/failed; `availability`: available/missing/changed (GET /v1/sources/{id} звіряє з файлом). POST /v1/sources повертає `hash_job_id`. На рестарті незавершені jobs → interrupted, а джерела з pending-хешем отримують новий hash job (інакше relink заблокований назавжди). Уточнено 2026-11-14: failed-хеш теж повертається в pending і перераховується, якщо файл за збереженим шляхом знову regular file з тим самим size і mtime_ns (`services/source_files.current_availability`); missing/changed лишаються failed. Хеш, що впав не через файл (HASH_FAILED), перераховується на кожному старті — по одному job, обмежено одним воркером.
- Relink: лише після обчисленого SHA-256; інший вміст → 409 SOURCE_MISMATCH; поки хеш не готовий → 409 SOURCE_HASH_PENDING/SOURCE_HASH_UNAVAILABLE.
- PATCH /v1/clips/{id}: title, start_ms, end_ms, categories (null = не змінювати); stale revision → 409 STALE_REVISION з `current_revision`, перевіряється до валідації значень. verified → stale лише за фактичної зміни меж. Те саме правило діє, коли рендер завершується після правки: межі кліпу ≠ межам snapshot → stale; зміна title/review під час рендеру лишає verified (уточнено 2026-11-14).
- Export profile `audio_mode`: selected (один глобальний stream index), none, all (усі audio streams джерела в порядку індексів, кожен зі своїм offset; `ExportRequest.audio_stream_indexes`). Інші значення → 422.
- `write_srt: true` у M1 → 422 SRT_REQUIRES_TRANSCRIPT: транскриптів ще немає (M3 під'єднає `build_clip_srt`); жодного тихого пропуску.
- Списки сортуються за (created_at, id); `utc_now` на Windows тикає ~15 мс, тож записи з однаковим часом ідуть за id — курсор стабільний.
- Export batch (T5b): порядок перевірок — 503 без FFmpeg → профіль і output_dir (422) → в одній write-транзакції проєкт/кліпи 404, чужий проєкт 422 CLIP_PROJECT_MISMATCH, аудіодоріжка 422 → 409 CLIP_NOT_APPROVED (details.clip_ids); частковий batch не створюється. Один worker на всі export jobs; порядок items — `snapshot_json.position`. Batch→job через `JobRepository.find_by_checkpoint`; шляхи manifest/catalog — у `checkpoint_json` job.
- Файли batch: `manifest_<batch_id>.json` і `catalog_<batch_id>.csv` в output_dir через temp + `os.replace`; пишуться і для failed/cancelled/partial_failed; batch, скасований у черзі, їх не має (paths = null).
- Перед рендером size і mtime_ns джерела звіряються з зареєстрованими: розбіжність → item SOURCE_CHANGED, файлу немає → SOURCE_UNAVAILABLE, FFmpeg не запускається; quick fingerprint звіряє движок.
- Статус batch: є cancelled item → cancelled, інакше succeeded/failed/partial_failed. Job: cancelled; failed, якщо жоден кліп не експортовано або не записано manifest/CSV; partial_failed → job succeeded. Progress export job: `{stage,total,completed,failed}`, де `completed` — усі завершені items (verified + failed + cancelled), тож значення не спадає; `failed` — лише failed (уточнено 2026-11-14).
- Cancel: queued → одразу cancelled без manifest; running → cancelling, FFmpeg зупиняється, незавершені items cancelled, готові зберігаються; повтор ідемпотентний (202); завершена або не-export job → 409 JOB_NOT_CANCELLABLE.
- Старт: `ExportService.recover()` переводить відкриті batch у failed/partial_failed, items — INTERRUPTED, кліпи — failed, видаляє лише temp із точним ім'ям движка (`.clipforge-<task_uuid>.part`). `Runtime.close()` зупиняє рендер без запису в БД.
- FR-001 (2026-11-14, рев'ю M1): PATCH /v1/projects/{id} `{name?, archived?}` → 200 (форма POST + `archived`); GET /v1/projects приховує архівні, якщо не `include_archived=true`. Порядок: 404 PROJECT_NOT_FOUND → 422 INVALID_PROJECT_NAME → 422 NO_CHANGES (порожнє тіло, та сама назва після trim або той самий стан архіву). docs/04 §4 таблиця маршруту не мала — це розширення контракту, не конфлікт.
- Перевірка виходу (2026-11-14): decode-check FFmpeg запускається з `-map 0`, тож повністю декодуються всі потоки, зокрема кожна доріжка audio_mode=all. Інтервал без жодного відеокадру → item `NO_VIDEO_FRAMES` (окремий прохід `-f null` з тим самим ланцюжком і `-progress frame=0`, не текст stderr; preseek → повтор full_decode), а не загальний FFMPEG_FAILED. Мінімальної тривалості кліпу API не вводить.
- Прогрес і діагностика export (2026-11-14, рев'ю M1): `on_progress` движка → progress_json `{stage: render|verify, total, completed, failed, item_percent}`; `item_percent` = out_time / тривалість кліпу в межах стадії (0–100, verify починає з 0), запис у БД не частіше ніж раз на 0,5 с, перший звіт кожної стадії — одразу. Відмова item → один WARNING `batch/item/code/detail`: хвіст stderr ≤4 КБ, шлях джерела, output dir і temp замінені на `<source>`/`<output>`/`<temp>`; detail ніколи не йде в API, БД чи manifest. `ExportService.recover()` після закриття batch пише manifest/CSV тим самим writer, що й звичайне завершення (best effort: немає output dir → paths = null, старт не падає).

## ADR 021 Відтворення в M2: прямий програвач або preview-proxy (2026-11-14)

- Контекст: docs/04 має лише GET /v1/sources/{id}/media і cleanup за `preview_id`, маршруту створення proxy немає. FR-029 і план M2 (п. 3) вимагають proxy з правильним timeline mapping. Це розширення контракту, не конфлікт.
- Прямий програвач (оригінал через app-media → /v1/sources/{id}/media) лише коли водночас: контейнер mov/mp4, відео h264, аудіо aac/mp3/opus або немає, `canonical_origin.origin_ms == 0`, і вибрана доріжка — перша аудіодоріжка джерела. Тоді `currentTime·1000 == canonical ms`. Інакше — одразу proxy. Помилка `<video>` (MEDIA_ERR_SRC_NOT_SUPPORTED/DECODE) на прямому шляху теж переводить на proxy. Причина консервативності: Chromium може мовчки відкинути непідтримуване аудіо (PCM у Matroska) без події error, а відлік currentTime при ненульовому PTS не перевірено емпірично (T-010).
- Preview-proxy: H.264 (libx264), висота ≤720 (без апскейлу), AAC стерео, keyframe щосекунди, `+faststart`, MP4; таймлайн починається з canonical zero, тривалість дорівнює тривалості джерела, без нормалізації швидкості, VFR зберігається. Пізній старт аудіо заповнюється тишею, як в export (ADR 018). Отже на proxy теж `currentTime·1000 == canonical ms`. Proxy ніколи не використовується для фінального export (FR-038).
- API (адитивно): `POST /v1/sources/{id}/previews {audio_stream_index: int|null}` → 202 `{id, job_id, status}`, або 200 з наявним `ready` preview для того ж (source, audio_stream_index, profile_version), якщо файл і size/mtime джерела не змінилися. `GET /v1/previews/{id}` → `{id, source_id, audio_stream_index, status, job_id, error}`. `GET /v1/previews/{id}/media` має ту саму семантику Range, що й медіа джерела; не `ready` → 409 PREVIEW_NOT_READY. Скасування — через POST /v1/jobs/{id}/cancel. Статуси: queued, running, ready, failed, cancelled, interrupted.
- Файли: `<data_dir>/cache/previews/<preview_id>.mp4`, через temp `.clipforge-<task_uuid>.part` + `os.replace`. Успіх лише після перевірки ffprobe (декодується, тривалість у межах допуску від тривалості джерела). На старті незавершені preview стають interrupted, видаляються лише temp з точним ім'ям движка. Оригінал лише читається.
- Уточнення (2026-11-14, M2 T9a): таблиця `previews` (source_id, audio_stream_index NULL = без звуку, profile_version=1, job_id, status, source_size/mtime, file_size, error_code); temp `.clipforge-<preview_id>.part` (ім'я виводиться з канонічного UUID, колонки temp_path немає). Ready перевикористовується лише при збігу size/mtime джерела і розміру файлу; POST для queued/running того ж ключа повертає його ж (202), другий job не створюється. Порядок перевірок POST: 503 без FFmpeg → 404 SOURCE_NOT_FOUND → 422 INVALID_AUDIO_STREAM → 400 SOURCE_UNAVAILABLE/SOURCE_CHANGED; тіло `{audio_stream_index}` обов'язкове, зайві ключі заборонені. Прогрес job `{stage: render|done|failed|cancelled, percent}`. HDR-джерело → failed HDR_UNSUPPORTED (не показувати вицвілу картинку як оригінал, docs/05 §2). Рецепт: libx264 veryfast crf 23 bf 0, keyframe щосекунди, `-fps_mode passthrough`, AAC 128k стерео, scale до 720 лише якщо висота >720; фільтри trim/atrim/setpts/aresample спільні з export_engine. Перевірка виходу — ffprobe (h264, ≤720, парні розміри, одна AAC-стерео або без звуку, старт≈0, тривалість ±100 мс), без повного decode-проходу. Cancel після `os.replace` → job succeeded (як в export). Маршрутів previews немає в docs/04 §4 — адитивне розширення контракту.

## ADR 022 IPC-шлюз main для M2 (2026-11-14)

- Renderer кличе backend лише через один канал `api:call {op, params}`; 12 op (з T4 — 14: + previews.create, previews.get; з M2 — 16: + sources.list, exports.retry; з Т17a — 17: + system.checks) з allowlist мають фіксовані method+path (`src/main/api-ops.ts`). Id — тільки uuid4, зайві ключі params → INVALID_PARAMS, невідома op → UNKNOWN_OP, без звернення до sidecar. Main перевіряє лише форму; доменні правила лишаються в backend (422).
- Відповіді sidecar проходять парсер op: renderer не отримує шлях оригіналу, `probe` і `canonical_origin` (рішення про прямий програвач/proxy рахує main). Шляхи експорту (`output_dir`, `final_path`, `manifest_path`) показуються як дані. Токен вирізається з сирого тіла (`[redacted]`), `details` помилок відкидаються.
- `Sidecar.request`: лише `http://127.0.0.1:<port>/v1/...`, `redirect:'error'`, таймаут 60 с, без повторів; збій POST/PATCH → `retryable:false` (неоднозначний результат не повторюється автоматично).
- Діалоги: `dialog:import-video {project_id}` — main сам робить POST /v1/sources з вибраним шляхом; `export:choose-folder` → `{token, displayName}`, шлях лишається в main. Токен теки одноразовий і згорає навіть при помилці backend (захист від дубля batch); при помилці форми не витрачається. Одночасно відкритий лише один діалог, повторний виклик → `{canceled:true}`.
- Bridge v2 (`bridgeVersion:2, getStatus, call, importVideo, chooseExportFolder`) у preload. Тип v1 прибрано в задачі renderer-оболонки M2 (T5); `src/shared/bridge.ts` має лише v2 (+ `openExportFolder`, `getViewState`/`setViewState` з M2; `pickVideo`, `takeDroppedVideo` з Т24 — ADR 024).
- Уточнення (2026-11-14, M2 T4): `app-media://source|preview/<uuid4>` — лише GET (інше → 405), будь-який інший URL → 404 без звернення до sidecar; назад ідуть тільки status, Content-Range, Content-Length, Accept-Ranges, Content-Type; відповідь не 200/206 — без тіла. Таймаут діє до заголовків, потік не обривається. `SourceDto.playback {direct, reason, direct_audio_stream_index}` рахує main (`src/main/playback.ts`); причини proxy: CONTAINER_UNSUPPORTED, VIDEO_CODEC_UNSUPPORTED, AUDIO_CODEC_UNSUPPORTED (перша аудіодоріжка), NONZERO_ORIGIN, PLAYBACK_INFO_MISSING. Renderer: direct лише якщо вибрана доріжка == `direct_audio_stream_index`. Мінімальне вікно 1100×720.

## ADR 023 Список джерел проєкту і дрібні рішення «Моментів» M2 (2026-11-14)

- GET /v1/sources?project_id&limit&cursor — адитивне розширення docs/04 §4 (у таблиці лише GET /v1/sources/{id}), потрібне, щоб після рестарту показати джерела проєкту. Порядок `(created_at, id)` і непрозорий курсор — як у GET /v1/projects; limit 1..100 (дефолт 50). Непорожній невідомий project_id → 404 PROJECT_NOT_FOUND (як POST /v1/sources), порожній → 422. Курсор з іншого проєкту не відкидається, але вибірка завжди обмежена своїм проєктом.
- Renderer «Моменти» (Т6a): вибране джерело й вибір кліпів для експорту живуть у ProjectView (переживають перемикання вкладок). Порожня назва кліпу → «Фрагмент HH:MM:SS.mmm–HH:MM:SS.mmm», не блокує збереження. Повзунок позиції `player-seek` додано понад список docs/03 §8 (без нього не можна переміщатися). Select аудіодоріжки — лише при ≥2 доріжках. Додаткові test IDs: reject-clip, reopen-clip, clip-start-here/clip-end-here, clip-start-minus/-plus, clip-end-minus/-plus, preview-clip, proxy-progress/-cancel/-error/-retry/-cancelled/-reason, player-*.
- `parseTimecode` у `shared/timecode.ts` має ту саму граматику, що backend `parse_timecode`; канонічні ms = round(currentTime·1000).
- Експорт з UI (Т7): `exports.retry {batch_id}` — main сам читає batch і бере його `output_dir`, `profile`, `project_id`; renderer шлях не передає (зайві ключі → INVALID_PARAMS). Відмова EXPORT_NOT_FINISHED для queued/running, NOTHING_TO_RETRY без failed/cancelled. `export:open-folder` відкриває лише наявну абсолютну теку batch (інакше EXPORT_FOLDER_MISSING). У renderer з `observed` доходить лише `duration_ms`. SRT показано вимкненим із поясненням (backend M1 відповідає 422 на `write_srt:true`); «Якість» — одне значення `high`. Порядок clip_ids — за порядком джерел. Вибір після запуску не очищується. При partial_failed export-complete показує «Експорт завершено частково: N з M не вдалося».
- Відновлення вигляду (M2): стан UI зберігає main у `<dataDir>/ui-state.json` (userData у production, CLIPFORGE_DATA_DIR у test mode), не renderer localStorage. Вкладка «Експорт» запам'ятовується як «Моменти» (batch живе лише в сесії). Повернення до списку проєктів стирає пам'ять. Невідомий проєкт → список без банера; збій читання списку → пам'ять лишається. Окремого projects.get немає — пошук сторінками projects.list. Відео при відновленні саме не стартує.
- Обсяг M2 (2026-11-14): панель «Що шукати» (категорії, custom instruction, find-highlights) переноситься в M4 — це T-031 «Unit/API/UI M4» і пункт 1 M4 у docs/02; у M2 без backend аналізу вона була б заглушкою («No placeholders in shipped code»). Тому review.spec E2E-04 очікувано не проходить до M4; вихідний гейт M2 — review.spec E2E-01..03 плюс власні Electron E2E (smoke, restart). Фільтри/сортування, панель details/transcript, badge «Перевірити картинку», таймлайн і віртуалізація списку — M5 (FR-029–035 разом з M4).
- Гарячі клавіші й редагування (Т6b): літерні клавіші — за надрукованою латинською літерою, на інших розкладках — за фізичною клавішею (`event.code`). A/R діють лише на `suggested`, як кнопки картки. Space не діє на кнопці/посиланні/вкладці (щоб не натиснути двічі). «Наступний» іде за порядком списку циклічно; нема чого перевіряти → `next-clip-status`. Правки й review одного кліпу йдуть чергою (review після правки бере нову ревізію). Чернетка зберігає лише змінені користувачем поля; після 409 «Зберегти мої значення» надсилає їх на новій ревізії, відкинути можна лише явно («Взяти збережені»). Глобального обробника Escape немає. Новий кліп не стає активним; «Створити фрагмент вручну» знімає активність.
- Розкладка «Моментів» (Т10): три колонки від 1440 px ширини сторінки, вужче — права панель стає вкладками під плеєром. Межі ширин: список 240–480 px, деталі 280–480 px, типово 320/320; плеєр не вужчий за 520 px. Ширини зберігаються в `ui-state.json` схеми v2 `{version:2, project_id, tab, layout:{list_px, details_px}}` зі строгою перевіркою; файл v1 читається з типовими ширинами; при списку проєктів файл, як і раніше, видаляється. Мінімум вікна 1100×720 задано для сторінки (`useContentSize: true`). Палітру не змінено (мінімальний контраст 4,92:1); прозорість disabled-кнопок лишилась (WCAG виключає неактивні контроли), натомість кожна недоступна основна кнопка має видиму причину. Тест контрасту — у src/main/renderer-styles.test.ts, бо renderer-tsconfig не має типів node.
- Відкладене з docs/03 за підсумком рев'ю M2 (2026-11-14), за пунктами docs/02: індикатор застарілого експорту («Цю версію вже експортовано», «Потрібен новий експорт») — M5.4; «Зберегти каталог» та історія batch — M5.5; очищення кешу preview (`POST /v1/cache/preview-cleanup`, dry preview) — M6.6; «Прослухати» аудіодоріжку для вибору STT-доріжки і «Налаштувати AI» на першому екрані — M3 (там з'являється ключ і вибір доріжки для транскрипції); контрольоване встановлення/вибір FFmpeg — M8. Активний кліп у редакторі зберігається автоматично (Т6b), окремої кнопки `save-clip` немає — вона лише у формі нового кліпу. Шляхи експорту в DTO renderer лишаються даними за ADR 022, переглянути в M6.3.
- Рішення власника (2026-11-14): екран першого запуску (docs/03 §3, без «Налаштувати AI» і встановлення FFmpeg), пошук/лічильники/остання дія/архівація в списку проєктів (§4) і drop zone (§5) робляться в M2. Перелік — docs/backlog.md.
- Частота кадрів і VFR (Т12a): `avg_frame_rate`/`r_frame_rate` для Matroska ненадійні (vfr.mkv дає 30/1 в обох), тому сканується PTS усіх пакетів основного відеопотоку (ffprobe, без декодування). `vfr=false`, якщо найдовший і найкоротший інтервали між сусідніми PTS різняться не більше ніж на 1 тік time_base; `frame_rate` — точний дріб (для CFR — `avg_frame_rate`, якщо він відтворює останній PTS). Скан обмежено min(timeout, 20 с); збій/таймаут → `vfr=null`, реєстрація не падає. У старих записах ключів немає → «невідомо».
- Стан збереження в шапці (Т15): пріоритет конфлікт > помилка > зберігаємо > збережено; у шапці лише мітка, текст помилки і «Спробувати ще раз» — у редакторі кліпу.
- Інспектор джерела (Т13): у M2 підпис лише «Відео залишається на цьому комп'ютері.». Речення docs/03 §5 «Для транскрипції надсилається вибране аудіо» з'явиться в M3 разом із транскрипцією, бо без неї воно неправдиве. Main додає до SourceDto `video {width, height, frame_rate, vfr}` лише з `probe`, як `playback` (ADR 021/022). Решта probe до renderer не йде. За rotation 90/270 main міняє місцями width і height (показується розмір, як його видно на екрані); сам ключ rotation до renderer не передається (`src/main/playback.ts`).
- Список проєктів (Т18, backend): пошук іде на сервері (`q`), бо список посторінковий і пошук у renderer бачив би лише завантажені сторінки. Збіг — підрядок назви через Python `str.casefold`, бо SQLite `lower()`/`LIKE` знають регістр лише ASCII. `q` обрізається; порожній `q` не фільтрує; задовгий → 422. `last_activity_at` — найпізніше з project.updated_at, sources.created_at, clips.updated_at і export_batches.created_at. Порядок і курсор не змінюються.
- Список проєктів (Т18, desktop): у M2 є лише архівування та повернення з архіву (docs/03 §4: «у версії 1 preferred archive»). Остаточне видалення даних застосунку з окремим підтвердженням складу даних у M2 не робиться. Originals не видаляються ніколи.
- Екран першого запуску (Т17): показується, коли немає жодного проєкту, включно з архівними. Готовність FFmpeg/FFprobe/папки даних дає новий GET /v1/system/checks; /v1/health не змінено, бо це контракт старту. У відповіді немає шляхів. `version` — версія з `-version`, отримана на старті, або null. `data_dir.ok` — у робочій теці вдалося створити й видалити власний тимчасовий файл; `free_bytes` — вільне місце на диску теки. Кнопка `new-project` лишається на цьому екрані (E2E-01 стартує з чистих даних). «Додати відео» створює проєкт з назвою за stem файлу (docs/03 §4) і реєструє джерело. Bridge для цього змінюється разом із drop zone (Т19), тож ADR пишеться перед Т17b.

## ADR 024 Вибране відео за токеном і drop zone (M2 Т17b, Т19) (2026-11-15)

- Контекст: «Додати відео» на першому екрані створює проєкт з назвою за stem файлу і лише потім реєструє джерело (ADR 023), а drop zone дає шлях із перетягування, не з діалогу. Якби main сам робив обидва кроки, renderer не дізнався б про проєкт, створений до збою реєстрації. Тому шлях вибраного відео, як і тека експорту (ADR 022), лишається в main за одноразовим токеном.
- Bridge v2 доповнюється адитивно (`bridgeVersion` лишається 2):
  - `pickVideo()` → канал `dialog:pick-video`; той самий діалог і фільтр, що в `dialog:import-video`. Відповідь `{token, fileName}` або `{canceled:true}`.
  - `takeDroppedVideo(file: File)` → preload приймає лише `File`, бере шлях через `webUtils.getPathForFile` (порожній рядок → помилка без IPC) і передає його тільки в main каналом `drop:video {path}`. Renderer шляху не отримує: preload не повертає його, відповідь та сама, що в `pickVideo`.
  - `importVideo` отримує другу форму `{project_id, file_token}`: main бере шлях за токеном і робить POST /v1/sources. Форма `{project_id}` (діалог + реєстрація) лишається для вкладки «Джерела».
  - Нова op `system.checks` → GET /v1/system/checks (ADR 023, Т17a) в allowlist `api:call`.
- Main перевіряє шлях із drop так само суворо, як вибраний у діалозі, і ще: рядок, абсолютний, без NUL, розширення з `VIDEO_EXTENSIONS` (без урахування регістру), `stat` — звичайний файл (тека → помилка). Помилки: `UNSUPPORTED_FILE` «Це не відеофайл. Перетягніть файл MP4, MOV, MKV…», `FILE_NOT_FOUND`. Текст помилки без шляху. Перевірка відправника (`isTrustedSender`) — на обох нових каналах.
- Токен відео: 32 випадкові байти hex, як токен теки, але окреме сховище. Одночасно дійсний лише останній виданий токен відео; він згорає при першому `importVideo` навіть при помилці backend; при помилці форми не витрачається. `fileName` — basename шляху (renderer і так бачить `display_name`).
- Назва проєкту — stem `fileName` (без останнього розширення), обрізаний пробілами й до 120 символів (PROJECT_NAME_MAX backend); порожній stem → «Новий проєкт». Рахує renderer.
- Сценарій першого екрана: `pickVideo` → `projects.create {name}` → `importVideo {project_id, file_token}` → відкрити проєкт на вкладці «Джерела». Якщо реєстрація не вдалася, проєкт лишається (видалення в M2 немає, ADR 023), renderer відкриває його з помилкою і звичайною кнопкою «Додати відео» для повтору.
- Drop zone (Т19): на першому екрані — той самий сценарій, що «Додати відео»; у вкладці «Джерела» відкритого проєкту — реєстрація в цей проєкт. Приймається рівно один файл; інакше «Перетягніть один відеофайл». Скинутий поза зоною файл ігнорується (renderer скасовує `dragover`/`drop` на документі; навігацію й так блокує `will-navigate`).
- Залишковий ризик: це перший IPC, де шлях приходить із процесу renderer. Код основного світу не має `ipcRenderer` (contextIsolation, sandbox), а `getPathForFile` дає шлях лише для справжнього файлу з диска, тобто того, який перетягнув чи вибрав користувач. Скомпрометований процес renderer міг би назвати будь-який відеофайл на диску; main приймає лише звичайний файл із розширенням відео, backend лише читає його через ffprobe без shell. Оригінал не змінюється. UNC- і device-шляхи (`\\host\share\x.mp4`) не відсікаються, бо діалог їх теж дозволяє і користувач може працювати з мережевою текою; `stat` такого шляху звертається до мережі (рев'ю M2, 2026-11-15).
- Уточнення (2026-11-15, Т24): невідомий, використаний або вже не останній `file_token` → `UNKNOWN_FILE_TOKEN` «Відео не обрано або вибір уже використано. Оберіть відео ще раз» (за зразком `UNKNOWN_FOLDER_TOKEN`). У `drop:video` нестрока, порожній чи відносний шлях, NUL, тека і не-відео розширення → `UNSUPPORTED_FILE`; будь-який збій `stat` → `FILE_NOT_FOUND` «Файл не знайдено або він недоступний. Перетягніть його ще раз»; payload не рівно `{path}` → `INVALID_PARAMS`. Порожній шлях із `getPathForFile` (картинка зі сторінки, blob) preload повертає як результат `UNSUPPORTED_FILE` без IPC; виняток TypeError лише для не-`File`. `pickVideo`, як і `dialog:import-video`, розширення й існування вибраного в діалозі файлу не перевіряє — це робить backend при реєстрації. Перелік ключів bridge у apps/desktop/e2e/smoke.spec.mjs доповнено `pickVideo`, `takeDroppedVideo`.
- Уточнення (2026-11-15, Т17b): перший екран вирішується додатковим запитом `projects.list {include_archived:true, limit:1}` лише коли звичайний список порожній і пошуку немає; збій цього запиту → `projects-error`. `projects-empty` лишився зовнішньою обгорткою `first-run`, а пошук і «Показати архівні» — на екрані, бо на них спираються restart.spec і projects.spec. «Додати відео» недоступна без FFmpeg або FFprobe (без FFprobe реєстрація гарантовано падає і лишає порожній проєкт), а також поки йдуть перевірки; причина видима й прив'язана `aria-describedby`. Якщо `system.checks` не відповів — кнопка доступна, поруч «Перевірити ще раз». На першому екрані основна дія одна: `new-project` тут не `primary`.

## ADR 025 Панель експорту в «Моментах» без перекриття (M2 Т16) (2026-11-15)
- Компактна панель експорту лишається липкою внизу `.main` (`bottom` = мінус padding `.main`, щоб доходити до краю вікна).
- Поки панель закріплена, хук `useClearOfStickyBar` (renderer/use-bar-room.ts) ставить на `<main>` `scroll-padding-bottom` = висота панелі + 8 px і стежить за висотою через `ResizeObserver`. Тому `scrollIntoView` і фокус із Tab зупиняються над панеллю.
- Коли підсумок експорту відкрито (`data-docked='false'`), панель стає `position: static` і стоїть у потоці після робочої зони, бо інакше висока панель закрила б «Моменти».
- Перевірка: layout.spec `auditExportBarCover` для 1100×720 і 1440×900 × 1/1,25/1,5. Після scrollIntoView `elementFromPoint` у центрі кожного ввімкненого контрола має повертати сам контрол (або його нащадок чи label), а контрол не повинен заходити під верх панелі.
- Уточнення ADR 023 (2026-11-15, Т26, рев'ю M2): перейменування проєкту (FR-001, docs/03 §4) робиться в M2: «Перейменувати» стоїть першим пунктом меню «Ще дії» рядка проєкту, поле відкривається в рядку. Окремого перейменування в шапці відкритого проєкту немає.

## ADR 026 Chunk planner M3 (2026-11-15)
- `MIN_CORE_MS = 5000`: це власне число проєкту, в docs його немає. Ядро ділиться навпіл лише тоді, коли кожна половина має щонайменше 5000 мс, тобто ядро від 10000 мс. Якщо 413 повертається на меншому ядрі, частина отримує failed, а не ділиться нескінченно.
- Payload рахується як верхня межа PCM WAV 16-bit mono 16 kHz: 44 байти заголовка плюс 32 байти на мс. Для 310 с це 9 920 044 байти. FLAC менший, тому межа консервативна. Ліміт бінарних даних 20 MiB. Запит рахується як base64 плюс 16 KiB JSON і має вкладатися в base64(20 MiB) плюс 64 KiB. Справжній ліміт транспорту задає capability адаптера через параметри `estimate_payload`.

## ADR 027 Імпорт транскрипту M3 (2026-11-15)
- Domain лишається тільки на stdlib (ADR 017), тому `jsonschema` не додано. У `domain/transcript_import.py` є вбудована копія `contracts/transcript.schema.json` і валідатор лише для потрібного підмножини ключових слів (type, const, enum, minimum, minLength, maxLength, required, properties, additionalProperties=false, items). Тести перевіряють дві речі: копія дорівнює контракту, а контракт не містить інших ключових слів. Будь-яка зміна контракту ламає тест. `1000.0` і `true` integer-ом не вважаються.
- Мова для SRT/VTT за замовчуванням `"und"`: API мову не передає, а схема вимагає 2–32 символи. Береться `duration_ms` джерела. `duration_ms` із документа звіряється тільки зі схемою.
- Репліки SRT/VTT стабільно сортуються за start, перекриття дозволені. Репліки з порожнім після очищення текстом відкидаються, нумерація йде підряд. 0 реплік → `TRANSCRIPT_NO_CUES`, порожній файл → `TRANSCRIPT_EMPTY`. Рядок із `-->` у тексті репліки вважається помилкою формату. Кома в часі VTT відхиляється.
- Normalized JSON: ordinals строго зростають, start не спадає, id унікальні серед words і segments разом, покриття впорядковане без перекриттів. Якщо offset ≠ 0, покриття обрізається до [0,D). Якщо offset = 0, воно вже має вкладатися в [0,D), інакше `TRANSCRIPT_OUT_OF_BOUNDS`.

## ADR 028 Злиття транскрипту і формат аудіо M3 (2026-11-15)
- Формат завантаження в STT — PCM WAV s16le mono 16 kHz. docs/05 дозволяє FLAC або WAV, але live probe підтвердив `"format":"wav"` для обох моделей, а FLAC для Gemini не перевірено. 310 с ≈ 9,92 МБ, base64 ≈ 13,2 МБ: це менше за ліміт проєкту 20 MiB і за 25 МБ OpenRouter (для провайдерів, крім OpenAI/Groq, більший base64 не приймається). OpenRouter обриває upstream-запит через 60 с, і вікно 300 с у це вкладається (47 с аудіо оброблялись 3–4 с).
- Час провайдера, що виходить за upload-вікно чанка більш ніж на 100 мс, вважається невалидним (`MERGE_INVALID_PROVIDER_TIMING`). До 100 мс включно час обрізається з діагностикою `TIMING_CLAMPED`. Невалидний час валить merge цілком із `chunk_core_start_ms`, тому оркестратор (Т7b) валідує відповідь адаптера до merge і помічає такий чанк failed.
- Дублікат на стику: обидва записи лежать в аудіо, яке чули обидва чанки, нормалізований текст (NFKC, casefold, без пунктуації й пробілів) однаковий, проміжок ≤ 200 мс. Пари шукаються один до одного, найближчі спершу. Лишається версія, чий midpoint ближче до власного ядра. Різний текст на стику дублікатом не вважається (відоме обмеження).
- Якщо хоч один чанк із мовленням без word timing, весь транскрипт стає `segment`, words порожні, по кожному такому чанку діагностика `SEGMENT_TIMING_FALLBACK`. Слова не синтезуються.
- Мова — найчастіша серед успішних чанків, за рівності береться раніша, якщо даних немає — `"und"`.

## ADR 029 Контракт STT adapter OpenRouter M3 (2026-11-15, Т5)
- Модуль `clipforge/adapters/openrouter_stt.py`, синхронний `httpx2.Client` (ADR 015; job-и працюють у потоках). Один виклик = одна спроба. Retry, Retry-After, backoff, split і бюджет — відповідальність оркестратора Т7b.
- Профілі: `microsoft/mai-transcribe-2` (provider options slug `azure`) і `google/gemini-3.5-transcribe` (без provider options). Тіло: `model`, `input_audio {data: base64, format: "wav"}`, `temperature: 0`, `response_format: "verbose_json"`, `timestamp_granularities: ["segment","word"]`, `language` лише якщо задано. `provider.options.azure` тільки для MAI і лише з переданих options. Значення за замовчуванням для verbatim визначає capability probe (Т5a), до нього adapter options не вигадує.
- Base URL production `https://openrouter.ai/api/v1`. У test mode береться `Config.test_provider_base_url`. Ключ передається аргументом і йде тільки в заголовок `Authorization: Bearer`. У тексті помилок, repr, логах і збережених тілах ключа немає. Таймаути: connect 10 с, write 60 с, read 120 с (OpenRouter обриває upstream через 60 с).
- Помилка `SttError(kind, status, retry_after_s, generation_id)`, повідомлення українською:
  - `auth` — 401/403, зупинка, «перевірте ключ у Налаштуваннях»;
  - `funds` — 402;
  - `rate_limited` — 429, Retry-After у секундах або HTTP-date;
  - `payload_too_large` — 413;
  - `model_unavailable` — 404;
  - `invalid_request` — 400/422 та інші 4xx;
  - `upstream` — 408 і 5xx;
  - `not_sent` — помилка з'єднання або connect/pool timeout до відправлення;
  - `unknown_outcome` — write/read timeout або обрив після відправлення: оплата невідома, автоповтору немає;
  - `invalid_response` — 200, але тіло не проходить валідацію.
- Валідація 200 (capability понад HTTP 200):
  - тіло — JSON-об'єкт, `text` — рядок;
  - кожне слово чи сегмент має текст і скінченні `start ≤ end ≥ 0`, інакше `invalid_response`;
  - елементи з порожнім текстом відкидаються з лічильником;
  - `language` і `duration` необов'язкові, `null` → None;
  - `speaker` і `confidence` за відсутності None;
  - слів немає, а текст непорожній → `has_word_timing = False`;
  - текст порожній і елементів немає → тиша (успіх).
- Результат: слова й сегменти як `domain.transcript_merge.ChunkItem` (секунди від початку завантаженого аудіо), а також text, language, duration_s, usage і generation_id.
  - `usage`: cost як `Decimal`, або None, якщо поля немає чи воно не число. Вартість не вигадується. Також seconds і tokens, якщо є.
  - `generation_id` — із заголовка `X-Generation-Id`, інакше None.
- Тести: httpx2 MockTransport на живих фікстурах `tests/fixtures/openrouter/{mai,gemini}_verbose.json`, а також фікстура 402 (тіло з known-issues). Живий виклик у тестах заборонено.
- Доповнення ADR 028 (Т2b): точка нульової тривалості від провайдера (start == end) — це наслідок гранулярності (Gemini 0,1 с), а не помилка. Інтервал стає [start, start+1 мс) з діагностикою, на верхній межі аудіо — [D−1, D). На word-рівні показані сегменти будуються зі слів, бо обидві моделі повертають один сегмент на все аудіо. Відоме обмеження: межа ставиться й після скорочень на кшталт «Dr.».
- Вказівка власника (2026-11-15): відео здебільшого англійською чи іспанською. Українська мова контенту не обов'язкова, `language:"uk"` не задаємо. За замовчуванням `language` не передаємо (автовизначення). Мову користувач може задати явно, напр. `en` чи `es`. Т5a перевіряє запит без мови та `es`, а не `uk`. UI лишається українським.

## ADR 030 Сховище транскриптів M3 (2026-11-15, Т4)
- `id` у транскрипт-API — це id незмінної ревізії (`transcript_revisions.id`). `revision` — номер 1, 2, 3… в межах джерела (`UNIQUE(source_id, revision)`, max+1 у `write_session`). Кожен імпорт, STT-run чи виправлення створює нову ревізію. `origin` ∈ import|stt|correction. CHECK зв'язує поля: stt ⇔ `run_id`, correction ⇔ `parent_id`. Offset імпорту зберігається в `metadata_json`.
- На відміну від docs/04 §3: у `transcript_runs` немає колонки `revision`, зв'язок іде через `revisions.run_id`. Слова й сегменти посилаються на `revision_id` (PK `(revision_id, id)`). `spend_entries.run_id` не має FK, бо посилається і на STT-, і на analysis-run; також є `UNIQUE(run_id, request_id)`.
- (Замінено ADR 031: мікродолари, r0004.) Гроші в `spend_entries` зберігаються як Float. Це рішення Т4. Т7a має перевірити його проти Decimal з адаптера (ADR 029) і порівнянь бюджету під lock.
- `word_ids` сегмента при імпорті normalized JSON беруться за часом: слова, що повністю лежать у сегменті. Для SRT/VTT список порожній.
- Ліміти імпорту: 5 000 000 символів, 400 000 елементів, інакше 422 `TRANSCRIPT_TOO_LARGE`. Рядки з NUL або одиночними сурогатами дають 422 `TRANSCRIPT_TEXT_INVALID`. Повідомлення помилок імпорту можуть цитувати рядок чи шлях запиту; так зроблено для діагностики.
- Т5 (уточнення ADR 029): у слові чи сегменті перевіряється `start ≤ end` і `end ≥ 0`. Трохи від'ємний start передається далі, і його обрізає merge у межах допуску 100 мс. Неправильний тип необов'язкових полів стає None. Від'ємна cost стає None. Для Gemini provider_options не надсилаються. Слова читаються лише з верхнього рівня `words`.
- Доповнення після рев'ю M3 (2026-11-15). Незмінність `transcript_revisions`, `transcript_words` і `transcript_segments` забезпечують SQLite-тригери `BEFORE UPDATE/DELETE … RAISE(ABORT,'TRANSCRIPT_IMMUTABLE')` (r0003), а не лише код сервісу. Таблиця `spend_entries` змінюваною лишається свідомо, бо стани резерву переходять один в одний.
- Сегменти зі слів (ADR 028, Т2b) мають власні числа: пауза ≥ `PAUSE_BREAK_MS`=1500 мс розриває сегмент; сегмент не довший за `MAX_SEGMENT_MS`=20000 мс (крім одного слова, довшого за цю межу); текст сегмента ≤ `MAX_TEXT_CHARS`=2000 символів (maxLength у contracts/transcript.schema.json). Числа калібрувальні, змінювати їх можна лише з тестами на live-фікстурах.
- Доповнення до ADR 029 після рев'ю (2026-11-15, Т5b). Відповідь 200, у якій непорожній `text` (після strip), але немає жодного придатного слова чи сегмента, дає `invalid_response`, а не тишу (docs/05 §4, T-021). Порожній `text` без елементів — валідна тиша. `OpenRouterStt(key, mode=..., base_url=...)` перевіряє адресу за правилом `resolve_base_url`: production — лише OpenRouter, test — лише loopback, OpenRouter у test mode відхиляється. Т7b створює клієнт як `OpenRouterStt(key, mode=config.mode, base_url=resolve_base_url(config))`.
- Доповнення до ADR 028 після рев'ю (2026-11-15, Т2c). Нульову тривалість визначає рівність після округлення до мс (`start_ms == end_ms`), а не рівність секунд. Перевернутий інтервал (`start_s > end_s`) лишається помилкою. У segment-fallback чанк із word timing дає сегменти з власних слів за правилами Т2b. Сегменти провайдера в такому чанку ігноруються й не валідуються. Сегмент провайдера в чанку без word timing довший за 2000 символів дає `MERGE_SEGMENT_TOO_LONG` з `chunk_core_start_ms`, а не загальну помилку тексту. Т7b має перевіряти кожну відповідь одразу через публічну `check_chunk(result)` (ті самі коди, що в merge, без перевірок усього джерела) і на `MERGE_SEGMENT_TOO_LONG` ділити це ядро, як при 413.

## ADR 031 Облік бюджету в мікродоларах (2026-11-15, Т7a)
- Замінює пункт ADR 030 про Float. Міграція r0004: `spend_entries.reserved_micro_usd` і `actual_micro_usd` (nullable) — цілі мікродолари (BigInteger). Наявні рядки конвертуються через `Decimal(repr(float))` з округленням вгору. CHECK обмежує state значеннями reserved|completed|unknown_outcome|released.
- Витрати (верхня оцінка, actual) округлюються вгору, ліміт (ceiling) — вниз. Тому `committed ≤ ceiling` у мікродоларах гарантує те саме в точних USD.
- Сума run = completed (actual, а якщо він невідомий — reserved) + reserved + unknown_outcome. released не рахується (FR-049).
- Переходи можливі лише з `reserved`; решта станів кінцеві (`SPEND_INVALID_TRANSITION`). Повторний `(run_id, request_id)` відхиляється навіть після release (`SPEND_DUPLICATE_REQUEST`), щоб один request_id не оплатився мовчки двічі. Перехід unknown → completed за generation_id — окреме рішення Т7b, якщо знадобиться.
- `SpendLedger.reserve` перевіряє й вставляє під `threading.Lock` і в одній `write_session` (`BEGIN IMMEDIATE`). Атомарність між кількома екземплярами тримає транзакція (T-048). Decimal у `price_snapshot` зберігається рядком.
- Перевищення бюджету — HTTP 429 з кодом `BUDGET_EXCEEDED` (docs/04 §4), `ErrorKind.LIMIT_EXCEEDED` (виправлено в Т7c; Т7a видавав CONFLICT).
- r0004: старий стан, якого немає в SPEND_STATES, стає `unknown_outcome`, тобто рахується в бюджет. Резерв такого рядка — max(reserved, actual): відома фактична сума не губиться (рев'ю Т7b, L4; Т7e1). Після downgrade/upgrade вихідний стан не відновлюється, це прийнято.

## ADR 032 Оркестрація STT-run M3 (2026-11-15, Т7b)
- Розбито на дві задачі. Т7b1 — сервіс `services/transcription_runs.py` без HTTP: виконує run над планом `domain/chunking`. Т7b2 — API, job, скасування і відновлення.
- Адаптер передається як Protocol `SttClient.transcribe(...)` з сигнатурою `OpenRouterStt.transcribe`. Аудіо: `extract_stt_audio` у `data_dir/stt/<run_id>/<chunk_id>.wav` (app-owned; оригінал лише читається). Сира відповідь: `data_dir/stt/<run_id>/<chunk_id>.json`, ключа в ній немає. Шлях пишеться в `response_path`. Сон і час передаються ззовні (clock/sleeper), тож у тестах реального очікування немає. Сон переривається скасуванням.
- Паралельно виконуються щонайбільше 2 частини (docs/05 §6), черга FIFO за core_start_ms.
- Кожна спроба має новий `request_id` (uuid4) і окремий резерв у `SpendLedger`. Ledger повторів не дозволяє (ADR 031). Резерв = `ceil(upload_ms/1000) × usd_per_second_upper` моделі. Без резерву запит не відправляється; резерв береться після витягу аудіо, безпосередньо перед відправленням (Т7b1a). `BUDGET_EXCEEDED` зупиняє run: решта частин стає `failed` з цим кодом, нові запити не йдуть.
- Верхні тарифи — це втричі живий probe 2026-11-15, округлений вгору: MAI 0,0001 $/с (спостережено ≈0,0000278); Gemini 0,0003 $/с (спостережено ≈0,000088, тариф токенний). Ціна з `price_snapshot` знімається на момент резерву разом із `basis: "live_probe_2026-11-15_x3"`. Це локальний контроль, а не гарантія рахунку провайдера (docs/05 §6).
- Підсумок спроби:
  - 200 і `check_chunk` OK → ledger.complete(actual = usage.cost, а якщо cost=None, то None) → частина `succeeded`;
  - `rate_limited` → release, чекати Retry-After (якщо його немає — експоненційно з jitter, база 2 с, межа 60 с), повторити;
  - `upstream` і `not_sent` → release, повторити з тим самим backoff;
  - на одну частину щонайбільше 3 спроби разом (T-025); після третьої частина `failed` з кодом останньої помилки;
  - `payload_too_large` і `MERGE_SEGMENT_TOO_LONG` → для 413 release, а для 200, що не пройшов `check_chunk`, complete (за відповідь заплачено); далі `ChunkPlan.split`; нащадки стають новими `pending`; на `CHUNK_BELOW_MIN_CORE` частина `failed` (T-027);
  - `auth`/`funds` → release, run зупиняється (`failed`, код `STT_AUTH`/`STT_FUNDS`), решта частин `cancelled` (T-026);
  - `invalid_request`, `model_unavailable` → release, частина `failed` без повтору (тіло те саме); `invalid_response` → complete(actual=None), частина `failed` без повтору (Т7b1a);
  - `unknown_outcome` → ledger.mark_unknown, частина `unknown_outcome`, автоповтору немає (T-028). Рішення повторити — лише явне (Т7b2: resume з `retry_unknown:true`).
- Завершення: коли всі частини в кінцевому стані, `merge_transcript` бере `succeeded` і створює ревізію `origin=stt` з `run_id` і coverage. Run стає `completed`, якщо coverage повний, і `partial`, якщо є failed/unknown/cancelled (T-029). Якщо немає жодної `succeeded`, run `failed` і ревізія не створюється.
- Кеш (T-030): `succeeded` частина з валідним `response_path` повторно не відправляється. Повтор run виконує лише частини не в `succeeded`. Відповідь читається з файла, а якщо файл зник або не проходить валідацію, частина знову `pending`.
- `transcript_chunks.reserved_cost/actual_cost` (Float з r0003) міграція r0006 замінює на `reserved_micro_usd/actual_micro_usd` (BigInteger, сума за всі спроби частини). Джерело правди лишається ledger.

## ADR 033 Налаштування і ключ API M3 (2026-11-15, Т7c, рев'ю)
- Таблиця `app_settings(key PK, value_json)` (r0005) зберігає лише чотири несекретні ключі: stt_model, stt_language, analysis_model, run_budget_usd. Скидання до default видаляє рядок. Збережене значення, що не проходить перевірку, ігнорується (береться default, у лог іде лише ім'я ключа). Так само поводиться рядок із пошкодженим JSON (зроблено в Т7d).
- PATCH атомарний: усе перевіряється до запису. Тіло — JSON-об'єкт: `{}` дає 200 без змін, запит без тіла — 422 VALIDATION_ERROR. Зайвий ключ дає 422. `stt_model: null` дає 422, бо default задано явно.
- run_budget_usd — десятковий рядок 0.01–1000, до 6 знаків після крапки, без знака, експоненти й початкових нулів; зберігається як введено. Межі — локальний запобіжник, їх можна змінити окремим рішенням.
- analysis_model — `vendor/model`, ASCII, ≤100 символів, рівно один `/`. Допускаються `~` на початку (аліаси OpenRouter) і `:`, `+`, `_`, `.`, `-` у назві моделі. Capability-тест моделі аналізу — M4.
- Ключ OpenRouter: `POST /v1/runtime/credentials` → 204. Ключ живе лише в пам'яті сайдкара (`CredentialStore`, SecretStr) і зникає при `Runtime.close()` та перезапуску. Постійну копію тримає main через safeStorage (Т8). Додатковий `DELETE /v1/runtime/credentials` → 204 (FR-048). Неправильний ключ дає 422 INVALID_API_KEY з фіксованим текстом, неправильна форма тіла — 422 VALIDATION_ERROR.
- Новий `ErrorKind.LIMIT_EXCEEDED` → HTTP 429 для локальних обмежень (бюджет, у майбутньому локальний rate).
- Доповнення до ADR 032 після приймання Т7b1 (2026-11-15):
  - Стан частини `superseded` (docs/05 §4) отримує ядро, яке розділили на нащадків; CHECK його допускає (r0006).
  - Статус run: `completed`, якщо покрито все; `partial`, якщо є ревізія, але не всі частини succeeded; `failed`, якщо жодна не succeeded або merge впав; `cancelled`, якщо скасував користувач і жодна не succeeded. Після зупинки (auth/funds/budget) run теж `partial`, якщо є успішні частини, бо вони вже оплачені й корисні. Код зупинки — `usage.error_code`.
  - У coverage контракту скасовані частини й ті, що не виконувались, позначаються як `pending`.
  - Retry-After обмежено 300 с (`MAX_RETRY_AFTER_S`). Після 429 пауза спільна для обох воркерів. Скасування перериває сон.
  - Перед першим запитом перевіряються size/mtime зареєстрованого джерела. Повторний запуск активного run → `TRANSCRIPTION_RUN_ACTIVE`; інші опції → `RUN_OPTIONS_MISMATCH`.
  - Відновлення: частина в стані `running` з резервом стає `unknown_outcome`, без резерву — `pending`. `retry_unknown=True` повторює `unknown_outcome` лише за явним рішенням (Т7b2: `POST /v1/jobs/{id}/resume`).
  - Кеш відповіді — JSON, серіалізований із `SttResult`: адаптер сире тіло не повертає, а ключа в ньому немає. WAV частини видаляється після спроби.
  - Виправлення під час приймання (Т7b1a). `invalid_response` — це 200, тобто ймовірно оплачено, тому `complete(actual=None)` (рахується резерв), а не release. Так само обробляється й несподіваний статус не-200, який адаптер теж повертає як `invalid_response`; облік тут свідомо консервативний. Резерв береться лише після успішного витягу аудіо: обрив під час FFmpeg не створює хибного `unknown_outcome`.
- Доповнення до ADR 032 після приймання Т7b2 (2026-11-15):
  - Job типу `transcription` виконує один воркер (`services/transcription_jobs.py`). Checkpoint містить {run_id, audio_stream_index, language, budget_usd}, а після завершення ще `error` за конвенцією `services/jobs.py`. Ключа в ньому немає. Ключ читається з `CredentialStore` лише в момент відправлення (`KeyedSttClient`); якщо ключа немає, це `auth`, якщо провайдер недоступний у цьому режимі — `invalid_request`, і в обох випадках нічого не надсилається.
  - Після перезапуску job стає `interrupted`, run — `interrupted` (новий статус), частини розбираються за правилом відновлення. Нічого не надсилається до явного `POST /v1/jobs/{id}/resume`.
  - Resume дозволено для job `transcription` у станах interrupted, failed, cancelled; run `completed` не відновлюється. Інакше 409 JOB_NOT_RESUMABLE. Спершу перевіряється `unknown_outcome` (409 UNKNOWN_OUTCOME_REQUIRES_DECISION з `count`), потім ключ (409 API_KEY_REQUIRED): без ключа всі частини впали б з STT_AUTH, а `unknown_outcome` втратив би позначку.
  - Підсумок job: run `completed` → `succeeded`; `cancelled` → `cancelled`; `partial` і `failed` → `failed` з error {code, message}. Тому частковий run можна дозапустити через resume, а його ревізія лишається доступною.
  - Ліміт у 3 спроби діє в межах одного запуску `run()`. Resume — явне рішення користувача, тож кожна незавершена частина отримує до 3 нових спроб; `transcript_chunks.attempts` рахує всі спроби разом (рев'ю Т7b, L1).
  - `progress` job записується лише після завершення; поточний стан частин показує `GET /v1/transcription-runs/{id}`.
  - Runtime без фабрики провайдера відхиляє кожен запит як `invalid_request`, нічого не надсилаючи. Test mode без `CLIPFORGE_TEST_PROVIDER_BASE_URL` поводиться так само (`resolve_base_url`).

## ADR 034 Ключ OpenRouter у main і екран «Налаштування» AI (2026-11-15, Т8)
- Bridge v2 доповнено трьома методами (адитивно): `setApiKey(key)`, `forgetApiKey()`, `getApiKeyStatus()`. Канали `settings:set-api-key`, `settings:forget-api-key`, `settings:get-api-key-status`; кожен обробник спершу перевіряє відправника. Відповідь — `{state: 'protected'|'session'|'none', message: string|null}`; `message` несе лише фіксований український текст для стану `none` (нечитаний файл). Ключ не повертається жодним каналом і не проходить через `api:call` (там `openrouter_api_key` дає INVALID_PARAMS).
- Main перевіряє форму ключа `[\x21-\x7e]{20,200}`. Спершу ключ передається sidecar (`POST /v1/runtime/credentials`); якщо sidecar відмовив (крім «ще не запущено»), нічого не змінюється. Якщо `safeStorage.isEncryptionAvailable()`, зашифровані байти пишуться в `<dataDir>/openrouter-key.bin` через тимчасовий файл і rename — стан `protected`. Інакше ключ лише в пам'яті main (`session`), а старий файл видаляється. `dataDir` — той самий каталог userData, що й для стану вигляду.
- Файл, який не читається або не розшифровується, дає `none` з фіксованим повідомленням і лишається на місці до наступного збереження чи видалення.
- «Видалити ключ» прибирає файл, копію в main і `DELETE /v1/runtime/credentials`. Якщо файл не видалився, нічого більше не змінюється.
- Main передає ключ sidecar на кожен перехід sidecar у `ready`. `app:get-status` віддає `ready` лише після цієї передачі, тому перший `settings.get` після перезапуску вже бачить `has_api_key: true`. Виклики сервісу ключа йдуть по черзі, тож передача не випередить збереження чи видалення.
- У логи йдуть лише коди помилок. Текст помилки sidecar, що йде в renderer, додатково очищується від ключа. Поле вводу очищується після збереження.
- Нові api-ops: `settings.get` (GET /v1/settings) і `settings.update` (PATCH, рівно чотири ключі ADR 033, `stt_model` не null).
- Кнопки «Перевірити ключ» у Т8 немає: backend-ендпоінт з'явився в Т9c (ADR 036), кнопка — Т9f.
- Т8b (після рев'ю): «нема backend» — лише sidecar, що не працює (`BACKEND_NOT_READY` або `BACKEND_UNAVAILABLE` при стані не `ready`, опція `backendRunning`). Транспортний збій чи таймаут POST/DELETE при `ready` повертається renderer як помилка. Якщо main уже не зберігає ключа, а backend повідомляє `has_api_key: true`, «Видалити ключ» лишається доступною з попередженням, і повтор знову шле DELETE.
- Т8b: `openrouter-key.bin.tmp` видаляється після невдалого запису чи rename і при forget; якщо він не видалився, forget вважається невдалим і нічого не змінює. Після невдалого forget екран перечитує стан у main і показує його разом із помилкою.
- Т8b: відкритий проєкт лишається змонтованим (прихованим) під «Налаштування», тож вкладка, export run і вибір кліпів зберігаються. Прихований проєкт не реагує на гарячі клавіші, плеер ставиться на паузу (`ViewActiveContext`, `useViewActive()`).
- Модель аналізу поки текстове поле, а не select (відступ від docs/03:85): перелік придатних моделей залежить від capability-тесту M4.

## ADR 035 Зупинка і продовження STT-run після рев'ю (2026-11-15, Т7e1, Т7e2)
- Доповнює ADR 032. Якщо воркер падає, сусідній воркер зупиняється ще всередині пулу. Після витягу аудіо, перед резервом, run ще раз перевіряє зупинку. Нова ревізія не прибирає попередню revision_id (Т7e1).
- Зупинка sidecar (`Runtime.close`) під час роботи: незавершений run і його job одразу стають `interrupted`, а не `cancelled` чи `partial`. Уже отримані відповіді зберігаються разом із ревізією. Частини, які зупинка не дала надіслати, стають `pending`, решта розбирається за правилом відновлення. Наступний старт бачить той самий стан.
- Якщо користувач уже скасував (job `cancelling`), зупинка завершує job як `cancelled`; зависання в `cancelling` немає. Run, що встиг стати `completed` до зупинки, лишається `completed`, а job — `succeeded`.
- Помилка сервісу у воркері спершу розбирає частини (як при падінні), потім завершує job як `failed`. Так само й під час зупинки: ServiceError дає `failed` з її кодом, бо повториться після перезапуску; неочікуваний дефект (`_abort`) під час зупинки дає `interrupted` (Т7f).
- Порядок перевірок `POST /v1/transcription-runs` (уточнено в Т7f): 422 (model, language, budget) → 503 MEDIA_TOOLS_UNAVAILABLE → джерело (404, 422 INVALID_AUDIO_STREAM) → ключ (409 API_KEY_REQUIRED) → під замком admission: 503 SERVICE_STOPPING, потім 409 TRANSCRIPTION_RUN_ACTIVE → одна транзакція run + chunks + job. Сервіс `transcription_jobs` пише run і частини через `TranscriptionRunService.create_run(session=...)`; дубля більше немає, перевірка джерела — спільна `require_source`. Порядок закріплено тестами.
- Resume: 422 budget → під замком admission 503 SERVICE_STOPPING → 404/409 JOB_NOT_RESUMABLE → далі як нижче. Спершу перевіряється інше відкрите завдання того самого джерела (409 TRANSCRIPTION_RUN_ACTIVE з run_id і job_id цього іншого завдання), потім `unknown_outcome`, потім ключ. Необов'язковий `budget_usd` перевіряється за правилом створення і замінює бюджет у checkpoint; без нього бюджет лишається попереднім.
- Запит перевіряється через `build_request_body` перед викликом клієнта: ValueError там стає STT_INVALID_REQUEST (резерв знімається, текст винятку не зберігається). ValueError із самого `transcribe` — дефект: частина стає `unknown_outcome`, резерв лишається, бо запит міг бути надісланий (Т7f).
- `shutdown` ставить прапорець під замком `_admission`; після нього create і resume відповідають 503 SERVICE_STOPPING без запису. Запит, що вже пройшов перевірки, встигає передати job воркеру; job, ще не взятий воркером, лишається `queued` до наступного старту, де стає `interrupted` (Т7f).

## ADR 036 Виправлення транскрипту і перевірка ключа (2026-11-15, Т9b, Т9c)
- Виправлення (`POST /v1/transcripts/{id}/corrections`) створює нову ревізію: origin `correction`, parent_id — виправлена ревізія, яка сама не змінюється. Змінюється лише text; час, id, ordinal, speaker, confidence і chunk_id копіюються.
- Вид правки задає timing_level ревізії: word → `word_id`, segment → `segment_id`; інший вид, змішані види чи дубль id → 422. Сегмент із виправленим словом отримує текст зі своїх слів через один пробіл (правило merge), інші сегменти не змінюються.
- Виправляти можна лише останню ревізію джерела: 409 TRANSCRIPT_REVISION_STALE {latest_id}, перевірка двічі (друга під write lock). Правка тим самим текстом теж створює ревізію. Позначення AI-оцінок застарілими (FR-020) — у M4.
- Перевірка ключа (`POST /v1/runtime/credentials/check`) — один `GET {base}/key`, без повторів і редиректів, таймаут 15 с. 401 → `{state:"invalid"}`, ключ у пам'яті лишається (видаляє його лише користувач). Решта збоїв → 503 retryable: KEY_CHECK_NOT_SENT, KEY_CHECK_UPSTREAM, KEY_CHECK_INVALID_RESPONSE. `label` не повертається.
- Перевірка виконується лише за явною дією користувача, не автоматично при збереженні ключа. Чи тарифікує OpenRouter `GET /key`, документація не каже.
- Т9g1 (після рев'ю): дедлайн 15 с діє на весь виклик, разом із з'єднанням і очікуванням заголовків: кожна операція сокета обрізається до залишку дедлайну (`_DeadlineTransport` підставляє мережевий backend у пул httpcore2 через приватний атрибут; версії закріплені в uv.lock, зламаний атрибут ловлять тести повільних заголовків). Резолв імені ОС перервати не можна, дедлайн перевіряється одразу після нього. ConnectError, ConnectTimeout і PoolTimeout → KEY_CHECK_NOT_SENT; WriteTimeout, ReadTimeout, обрив → KEY_CHECK_UPSTREAM. Обидва httpx-клієнти (ключ і STT) мають `trust_env=False`: проксі з оточення не використовуються. Запит ключа надсилає `Accept-Encoding: identity`.

## ADR 037 Оцінка перед запуском STT і захист від повторної оплати (2026-11-16, Т9a)
- `POST /v1/transcription-runs/estimate` {source_id, audio_stream_index, model?, language?, budget_usd?} → 200. Нічого не записує й не надсилає, ключ і FFmpeg не потрібні. model, language і budget_usd за відсутності беруться з налаштувань і перевіряються як у create (ті самі коди 422); бюджету немає — це не помилка, а `budget_usd: null`. Невідоме джерело → 404 SOURCE_NOT_FOUND, відсутня доріжка → 422 INVALID_AUDIO_STREAM.
- Відповідь: {source_id, audio_stream_index, model, language, duration_ms, chunk_count, billed_seconds, usd_per_second_upper (десятковий рядок), estimate_micro_usd, price_basis, budget_usd (рядок|null), within_budget (bool|null), existing ({transcript_id, run_id}|null)}.
- План — той самий `plan_chunks(duration_ms).active`, що в create; billed_seconds = Σ ceil(upload_ms/1000) по частинах; estimate_micro_usd = Σ `to_micro_usd(usd_per_second_upper × billed_seconds частини)` (кожна частина округлюється вгору, як резерв у ledger), тобто рівно сума перших резервів. Повтори, split і перекриття після split можуть додати витрат: це верхня оцінка однієї спроби на частину, а не межа рахунку (docs/05 §6). within_budget = estimate ≤ бюджет.
- FR-050: `POST /v1/transcription-runs` приймає `force: bool` (strict, за замовчуванням false). Якщо для джерела є run зі статусом `completed`, тією самою model, provider і `options_hash` (доріжка, мова), а його ревізія існує, і `force` не true → 409 TRANSCRIPT_ALREADY_EXISTS {transcript_id: revision_id цього run, run_id}; нічого не записано. Перевірка — після джерела (404/422) і до ключа (409 API_KEY_REQUIRED). Run `partial`/`interrupted` не блокує create: його дозапускають через resume. Імпортований транскрипт не блокує STT. estimate показує той самий збіг у `existing`.
- `GET /v1/transcription-runs?source_id=` → {items}: усі run джерела, новіші перші (created_at, потім id), кожен — як GET run без `chunks` плюс `created_at`. source_id обов'язковий (422 VALIDATION_ERROR), невідоме джерело → 404 SOURCE_NOT_FOUND. Без пагінації: run одного джерела небагато.

- Доповнення до ADR 037 (2026-11-16, рев'ю Т9a). Збіг для 409 TRANSCRIPT_ALREADY_EXISTS — source_id + model + provider + options_hash (audio_stream_index, мова, provider options). Це вужче за FR-050: хеш файлу джерела і профіль витягу аудіо в ключ не входять. У межах одного source_id хеш сталий (relink вимагає збігу), профіль витягу один (ADR 028). Той самий файл, доданий як інше джерело (інший проєкт), захисту не має і буде оплачений знову. Повторне використання транскрипту між джерелами — окрема задача (backlog). `source_id` у `GET /v1/transcription-runs` обмежено 200 символами: довший дає 422, а не 404.

## ADR 038 Запуск розпізнавання з desktop (2026-11-16, Т9d)

- Нові op allowlist (main/api-ops.ts, shared/api.ts): `transcription.estimate` {source_id, audio_stream_index} → POST /v1/transcription-runs/estimate; `transcription.create` {source_id, audio_stream_index, force?} → POST /v1/transcription-runs; `transcription.get` {id} → GET /v1/transcription-runs/{id}; `transcription.list` {source_id} → GET /v1/transcription-runs?source_id=; `jobs.resume` {id, retry_unknown?} → POST /v1/jobs/{id}/resume. Інших полів не приймати (exact).
- Модель, мова й бюджет renderer не передає: backend бере їх із settings (ADR 033), тож запуск відповідає екрану «Налаштування». Ключ у жодному op не фігурує.
- `details` помилок через bridge не передаються (ADR 024). «Транскрипт уже є» renderer бачить з `estimate.existing`, а 409 TRANSCRIPT_ALREADY_EXISTS на create лише показує те саме повідомлення.
- UI — блок «Розпізнавання мовлення» в SourceInspector («Джерела»). Підсумок з estimate: тривалість, модель, мова («Автовизначення», якщо null), частини, «до $X» (округлення вгору до цента), ліміт бюджету. Кнопка «Розпізнати мовлення» стартує run лише після показаного підсумку. Без ключа (409 API_KEY_REQUIRED) — «Відкрити Налаштування». Якщо є `existing` — «Транскрипт уже є» і окрема «Розпізнати ще раз (платно)» з force.
- Прогрес: опитування `transcription.get` (1 с, лише поки вид активний, `useViewActive()`); лічильник «Розпізнаємо мовлення · N із M частин» за станами частин; «Скасувати» → jobs.cancel. Стан після завершення — з `jobs.get` (error.code).
- Після закриття/повернення до джерела стан відновлюється з `transcription.list` (найновіший run). partial/failed із невдалими частинами — «Повторити невдалі» (resume). Частини `unknown_outcome` — «Відповідь не отримано. Провайдер міг обробити запит» і окреме підтверджене «Надіслати ще раз» (`retry_unknown: true`), без суми. interrupted/cancelled — «Продовжити». Тихого повтору немає.
- Т9d розбито: Т9d1 — op і парсери з тестами; Т9d2 — UI.
- Доповнення (Т9d2, прийнято 2026-11-16): ключ перевіряється заздалегідь за `settings.get.has_api_key`; блок перечитує settings, estimate і list, коли вид знову активний; за unknown_outcome «Повторити невдалі»/«Продовжити» приховано, лишається «Надіслати ще раз» із підтвердженням (`retry_unknown:true`); відкрите завдання (queued/running/cancelling) — активний запуск, навіть якщо run ще в старому статусі; помилки читання — `role="status"`, помилки дій — `alert`. Т9d3: без ліміту витрат (`estimate.budget_usd === null`) старт заблоковано заздалегідь з причиною й «Відкрити Налаштування» (backend інакше дав би 422 BUDGET_REQUIRED); підпис інспектора доповнюється реченням docs/03 §5 «Для транскрипції надсилається вибране аудіо.» (ADR 024 відклав його до M3).
- Доповнення 2 (рев'ю Т9d1+Т9d2, medium M1): run, зупинений BUDGET_EXCEEDED, не мав виходу (ліміт лежить у checkpoint, resume без `budget_usd` повторює ту саму зупинку), а partial/failed/interrupted/cancelled не давав повернутися до старту. Рішення: (1) `jobs.resume` приймає необов'язковий `budget_usd` (десятковий рядок за правилом `run_budget_usd` налаштувань) — це змінює попереднє «без budget_usd». Renderer шле його лише кнопкою «Продовжити з лімітом $Y» для завдання з error.code BUDGET_EXCEEDED; Y — поточний `run_budget_usd` з «Налаштувань» (без ліміту — кнопка веде в «Налаштування»). Уже оплачені частини run не надсилаються знову. (2) «Почати заново (платно)» для run partial/failed/interrupted/cancelled повертає до підсумку старту (свіжий estimate, вибір доріжки) з приміткою, що новий запуск надішле все аудіо знову: кеш частин діє лише в межах одного run. (3) Після неоднозначної невдачі create/resume (REQUEST_TIMEOUT, BRIDGE_ERROR, 5xx) блок перечитує стан до того, як старт знову стане доступним (CLAUDE.md: ambiguous paid timeout не повторюється мовчки). (4) «Відкрити Налаштування» також біля причини завдання STT_AUTH, STT_FUNDS і BUDGET_EXCEEDED.
- Доповнення 3 (Т9d4a прийнято): для завдання BUDGET_EXCEEDED звичайні «Продовжити»/«Повторити невдалі» приховано (вони повторили б ту саму зупинку). Якщо в такого завдання є частини unknown_outcome, підтвердження «Так, надіслати ще раз» шле `jobs.resume {id, retry_unknown:true, budget_usd:Y}` з поточним лімітом, а питання називає цей ліміт (Т9d4c); без ліміту в «Налаштуваннях» — лише «Відкрити Налаштування». Стан «повернулися до підсумку» після «Почати заново» живе лише в пам'яті блоку; після перемонтування знову видно зупинений run із тією самою кнопкою. Джерело з availability `missing` або `changed`: старт і продовження вимкнені з видимою причиною (backend і так відмовив би до надсилання).

## ADR 039 Транскрипт у desktop: панель, імпорт субтитрів, перевірка ключа (2026-11-16, Т9e, Т9f)

- Нові op (exact): `transcripts.list` {source_id, cursor?} → GET /v1/transcripts?source_id= (ревізії за зростанням: найновіша — остання на останній сторінці; renderer іде за `next_cursor`); `transcripts.get` {id, offset?, limit?} → GET /v1/transcripts/{id} (вікно сегментів і слів, `next_offset`); `transcripts.correct` {id, edits:[{word_id|segment_id, text}]} → POST /v1/transcripts/{id}/corrections; `credentials.check` {} → POST /v1/runtime/credentials/check ({state:"valid", is_free_tier, limit_remaining_usd} | {state:"invalid"}). Ключ у жодному op не фігурує.
- Імпорт SRT/VTT — новий канал main `dialog:import-transcript` {source_id, offset_ms?}. Main відкриває native dialog (.srt, .vtt), визначає формат за розширенням, читає файл сам: більше 20 МБ відмовляє ще до читання, декодує UTF-8 строго і знімає BOM. Потім шле POST /v1/transcripts/import. Шлях і сирий текст файлу в renderer не потрапляють і не логуються (уточнення про цитату в помилці розбору — у доповненні за рев'ю нижче); renderer отримує `cancelled` або TranscriptDto. Shell не викликається. Імпорт працює без ключа.
- Панель «Транскрипція» — третя частина DetailsPanel на «Моментах» (поряд із «Межі», «Клавіші»), для джерела активного кліпу. Найновіша ревізія вантажиться сторінками по 1000. Сегменти з часом показуються як plain text. Клік по часу перемотує плеєр (`seekTo(start_ms)`). Пошук — локальний, без урахування регістру, з лічильником і переходами; збіги підсвічуються `<mark>` із розбитого рядка, без innerHTML. Пропуски покриття (спани зі станом не `succeeded`) показуються списком із часом, клік по пропуску перемотує. Без транскрипту — підказка перейти на «Джерела».
- Виправлення (FR-020) — «Виправити» біля сегмента. У ревізії зі словами поле для кожного слова: кількість слів і час не змінюються, шлються лише змінені слова. У сегментній ревізії — один textarea до 2000 символів. «Зберегти» створює нову ревізію, панель переходить на неї. Помилки показуються біля поля. Гарячі клавіші під час набору не діють.
- «Перевірити ключ» — у блоці AI «Налаштувань», лише коли ключ є. Результат: «Ключ дійсний» + залишок ліміту або «Ліміт витрат для ключа не задано»; «OpenRouter не прийняв ключ»; помилки KEY_CHECK_* — текст backend (див. доповнення за рев'ю). Про ціну перевірки нічого не обіцяти.
- Розбиття: Т9e1 — op і парсери; Т9e2 — панель (перегляд, пошук, перемотка, пропуски); Т9e3 — виправлення; Т9f1 — канал імпорту в main і preload; Т9f2 — кнопки імпорту («Джерела») і «Перевірити ключ».

- Доповнення (Т9e2, Т9e3): панель читає транскрипт джерела робочої області (воно ж джерело активного кліпу) і показується без активного кліпу; `test-bridge` за замовчуванням відповідає порожнім `transcripts.list`. Поки відкритий редактор виправлення, інші «Виправити» вимкнені, щоб набраний текст не губився мовчки; фокус повертається на «Виправити» сегмента після збереження, «Скасувати» й Escape; під час перечитування після збереження на екрані лишається попередня ревізія.
- Доповнення (Т9f1): 20 МБ = 20×1024×1024 байт. Файл з іншим розширенням → TRANSCRIPT_FILE_UNSUPPORTED «Оберіть файл субтитрів у форматі SRT або VTT»; помилки читання → TRANSCRIPT_FILE_TOO_LARGE, TRANSCRIPT_FILE_ENCODING, TRANSCRIPT_FILE_UNREADABLE з фіксованим текстом без шляху. Відповідь каналу — `{canceled:true}` (написання як у `dialog:import-video`) або ApiResult<TranscriptDto>; `offset_ms` за замовчуванням 0.
- Доповнення (рев'ю Т9e2–Т9f2, Т9h1, Т9h2; 2026-11-16): код став точнішим за початковий текст ADR, діє таке.
  - Ліміти імпорту. Main читає файл обмежено: stat, потім через file handle не більше 20 МіБ + 1 байт; що більше 20 МіБ — TRANSCRIPT_FILE_TOO_LARGE, навіть якщо файл виріс після stat. Після декодування текст понад 5 000 000 кодових точок (MAX_IMPORT_TEXT_CHARS backend) теж TRANSCRIPT_FILE_TOO_LARGE, і нічого не надсилається. 20 МіБ (20 971 520 байт) більше за 4 байти × 5 000 000 + BOM: байтова межа не відкидає файл, який backend прийняв би.
  - `source_id` імпорту — uuid4, як в інших op (backend приймає 1–200 символів, але джерела застосунку мають uuid4).
  - Помилки розбору SRT/VTT від backend показуються як є. Вони можуть цитувати до 40 символів поганого фрагмента файлу, який користувач сам обрав (`domain/transcript_import.py`), щоб той знайшов рядок. Це не виняток із правила «сирий текст файлу не йде в renderer»: після успішного імпорту панель показує весь розібраний текст, тож фрагмент у помилці не розкриває нічого нового. Цитата не логується й не потрапляє в маніфести. Шлях не передається ніколи.
  - Панель читає найновішу ревізію до 500 сторінок по 1000 (backend віддає до 400 000 сегментів і слів). Далі TRANSCRIPT_PAGES_EXCEEDED. Список сегментів не віртуалізований (known-issues).
  - Виправлення. Текст обрізається (trim) і до порівняння, і перед відправкою. «Зберегти» вимкнене з видимою причиною: немає змін, порожнє поле, частину слів не завантажено. Після невдалого збереження фокус повертається на перше поле. При 409 TRANSCRIPT_REVISION_STALE під повідомленням є «Оновити транскрипт»: закриває редактор і перечитує найновішу ревізію. Escape під час IME-композиції редактор не закриває. Пошук прокручує лише список сегментів.
  - «Перевірити ключ». Ліміт `null` → «Ліміт витрат для ключа не задано»; ≤ 0 → «Ліміт витрат ключа вичерпано»; інакше «Залишок ліміту: $X». Помилки KEY_CHECK_* і API_KEY_REQUIRED — текст backend (`adapters/openrouter_key.py`), окремих текстів у renderer немає.
  - Новий імпорт прибирає попередній результат одразу після натискання, тож і скасований діалог його прибирає.

## ADR 040 Кінець відео Matroska: повторне читання, якщо пошук до кінця порожній (2026-11-17, Т9h7)

- Контекст: для Matroska (немає `duration_ts` потоку) кінець відео береться з пакетів від останнього ключового кадру: `-read_intervals "<кінець контейнера>%"`. У повному backend pytest FFprobe 8.1 на Windows інколи повертав на цей виклик порожній список пакетів з кодом 0 (known-issues; причину не знайдено).
- Рішення: якщо пошук не дав жодного придатного пакета, пакети цього відеопотоку читаються ще раз без `-read_intervals` (увесь потік). SourceUnreadableError «Не вдалося визначити тривалість відео» — лише коли і друге читання порожнє. Без `-read_intervals` (контейнер без тривалості) повтору немає: перше читання вже повне.
- Наслідки: у рідкісному випадку перевірка джерела робить ще один повний прохід пакетів відео. Найгірший час кроку — два виклики з лімітом `timeout_s` кожен, усередині запиту реєстрації джерела; загального дедлайну немає. На довгих джерелах час і пам'ять не вимірювалися.

## ADR 041 Відбір моментів M4: модель, вікна, перевірка, дедуплікація, run (2026-11-17)

Контекст: docs/06, FR-007–012, FR-020–028, FR-049; acceptance T-031, T-033, T-035; E2E-04. Розділи нумеровані, задачі M4 посилаються на них.

§1 Модель і ціна. Модель аналізу — `model` запиту, інакше `analysis_model` налаштувань, інакше 422 ANALYSIS_MODEL_REQUIRED. Приймається лише модель із перевіреної таблиці `analysis_profiles(mode)` (adapters/openrouter_chat.py): model, prompt/completion cap у USD за 1 млн токенів (Decimal), context_tokens, max_tokens, price_basis. Інша модель → 422 ANALYSIS_MODEL_NOT_SUPPORTED. У production таблиця порожня, доки власник не виконає live probe (`scripts/analysis_probe.py`, Т10): docs/01 забороняє вшивати непідтверджений model ID. До того AI-пошук у production недоступний з чесним повідомленням; ручне нарізання й імпорт працюють. У test mode є лише `test/selector` (cap 1 і 2 USD/Мтокен, context 128 000, max_tokens 4096). Cap надсилається як `provider.max_price` (OpenRouter не маршрутизує до дорожчого провайдера), тому резерв — справжня верхня межа. Також надсилається `provider.require_parameters: true`, щоб response_format не ігнорувався мовчки. Чи `max_price` приймає числа, перевіряє probe. (Уточнено §24: probe пройдено, у production є `anthropic/claude-haiku-5.5`, `max_price` лишається рядками.)

§2 Ключ, бюджет, резерв. Production без ключа → 409 API_KEY_REQUIRED. У test mode (лише loopback-провайдер, `resolve_base_url`) ключ не потрібен: acceptance не задає ключа. Це відмінність від STT, яку свідомо фіксуємо. `budget_usd` — JSON-число (не bool) або десятковий рядок за правилом `run_budget_usd` (0.01–1000, до 6 знаків), інакше 422 INVALID_RUN_BUDGET. Без бюджету в запиті й налаштуваннях → 422 BUDGET_REQUIRED. Резерв запиту в мікродоларах, округлення вгору: ⌈(байти UTF-8 усіх messages + байти компактного JSON `response_format` + 512) × prompt_cap + max_tokens × completion_cap⌉. Cap у USD за 10⁶ токенів дорівнює мікродоларам за токен, тому ділення немає (виправлено 2026-11-17 за звітом Т6a; початковий текст із «/ 10⁶» давав USD). Схему враховано, бо провайдер може рахувати її як вхідні токени (≈1,4 КБ). Кількість токенів не перевищує кількості байтів. Фіксується `usage.cost` відповіді; без нього — повний резерв як фактична сума.

§3 Одиниці й вікна (domain/analysis_windows.py). Рівень: сегменти, якщо в ревізії є хоч один, інакше слова; рівні не змішуються. `timing_level` запиту — рівень одиниць. Розмір одиниці: байти компактного JSON {id, ordinal, start_ms, end_ms, text} (ensure_ascii=False) + 1. `plan_windows(units, max_window_bytes, core_min_ms=300000, core_max_ms=480000, context_ms=60000, context_max_bytes=max_window_bytes//8)`; max_window_bytes ≥ 32768 = min(98304, context_tokens − max_tokens − 4096). Ядра йдуть підряд і покривають усі одиниці, кожна одиниця в одному ядрі, мінімум одна одиниця. Ядро росте, доки проміжок часу ≤ core_max_ms і байти ≤ max_window_bytes − 2·context_max_bytes. Якщо проміжок досяг core_min_ms, розріз ставиться на найбільшій паузі між сусідніми одиницями серед допустимих точок (за рівності — пізніша). Контекст: попередні одиниці зі start_ms ≥ core.start − context_ms і наступні з end_ms ≤ core.end + context_ms, у межах context_max_bytes, ближчі першими. Кандидат належить вікну, у чиєму ядрі лежить його start unit. Порожній транскрипт дає 0 вікон: run completed, запитів і кліпів немає.

§4 Запит. System — prompts/select.system.md; repair — prompts/repair.system.md. Копії лежать у `clipforge/resources/`, тест перевіряє їх побайтову рівність із prompts/*.md і contracts/selection.schema.json. prompt_version = "sha256:" + перші 16 hex sha256(select ‖ 0x00 ‖ repair ‖ 0x00 ‖ schema). schema_version = 1. User — компактний JSON {source_context: {language, duration_ms}, profile: {categories, custom_instruction, min_duration_ms, max_duration_ms, max_candidates}, timing_level, units}. Імені файлу й шляху немає. Repair-запит: той самий об'єкт + `validation_errors` (до 50 рядків) + `previous_output` (сирий текст, до 65536 байт). Тіло: model, messages [system, user], response_format {type: json_schema, json_schema: {name: "clipforge_selection", strict: true, schema}}, max_tokens, provider {require_parameters: true, max_price: {prompt, completion}}, stream false. temperature не надсилається. Відповідь читається до 1 МіБ.

§5 Розбір і перевірка (domain/selection_output.py). `parse_selection_output(text)` суворо відтворює contracts/selection.schema.json: точні ключі, int не bool, оцінки 0..4, довжини, унікальність, enum. Також відкидаються дублікати ключів JSON, NaN/Infinity, текст понад 262144 байти, title з керівними символами (Cc) і reason з Cc, крім \n. Помилки — англійською, зі шляхом (`candidates[0].start_id: unknown unit id`); id обрізаються до 64 символів. `validate_candidates(candidates, units, core_ordinals, selected)`. Жорсткі помилки (дають repair): id, якого немає серед одиниць цього запиту; start.ordinal > end.ordinal; evidence поза включним проміжком ordinal. М'які відкидання (без repair, у діагностику): CATEGORY_NOT_SELECTED (немає перетину з профілем) і NOT_OWNED (start unit поза ядром). Категорії моделі зберігаються всі (вони з повного enum); вимагається лише перетин. visual_review_required примусово true для action і unexpected (FR-023). evidence_type завжди `transcript`. Невідомий id не виправляється «найближчим». Будь-яка жорстка помилка, невалідний JSON, порушення схеми або finish_reason `length` дають одну repair-спробу на вікно. Повторна помилка — вікно failed ANALYSIS_INVALID_OUTPUT, run failed, кліпів немає (FR-027).

§6 Межі, rank, поріг (domain/selection_scoring.py). rank = (20·clarity + 15·hook + 25·completeness + 15·emotion + 10·novelty + 15·relevance + 2) // 4: ціле, docs/06 §6 з округленням .5 вгору. Поріг: rank ≥ 60 і completeness ≥ 2, інакше LOW_QUALITY. Evidence interval = [start_unit.start_ms, end_unit.end_ms). Відкидання: OUT_OF_SOURCE (поза 0..duration джерела), LONGER_THAN_MAX (evidence довше за max). Padding: pre = min(3000, es), post = min(4000, duration − ee). Якщо разом довше за max, надлишок знімається з padding пропорційно (cut_pre = надлишок·pre // (pre+post), решта з post); evidence не ріжеться. Recommended коротший за min → SHORTER_THAN_MIN (P1-перемикач «поза тривалістю» — M5). Кліп створюється з start/end = recommended; evidence interval зберігається окремо.

§7 Дедуплікація, різноманітність, ліміт (domain/selection_dedupe.py). Порівнюються інтервали одного джерела: overlap/union ≥ 0.65 або overlap/min_len ≥ 0.8. Duplicate = часовий сигнал + спільний evidence id. Якщо evidence наявного кліпу непорівнянні (`None`: ручний кліп або id, яких немає в поточному транскрипті), достатньо часового сигналу. Однакові слова в різний час не зливаються. Порядок: кандидати за rank ↓, start ↑, key ↑. (1) Дубль approved/rejected/ручного кліпу → suppressed `already_reviewed`. (2) Дубль наявного suggested → `duplicate_of_suggested`: старий кліп не змінюється. Оновлення старих застарілих suggested відкладено до M5. (3) Дубль уже прийнятого кандидата run → `duplicate_in_run`: злиття в нього (об'єднання категорій, evidence в межах його інтервалу, visual OR), без нової копії (FR-026). Потім різноманітність: жадібний вибір серед кандидатів із rank ≥ (найкращий з решти − 5). Перевага кандидату, у якого найменша кількість уже вибраних за будь-якою з його категорій. За рівності — rank ↓, start ↑, key ↑. Слабша сцена не проходить заради категорії. Ліміт max_candidates — після dedupe; решта → `over_cap`. Усі suppressed і відкинуті з повними даними — у diagnostics run.

§8 Зберігання (r0007). `analysis_runs`: id, source_id FK, transcript_id FK, transcript_revision, profile_json, model, provider, prompt_version, schema_version, unit_level, price_snapshot_json, status (queued/running/completed/failed/cancelled/interrupted), error_code, diagnostics_json, created_at, updated_at. `analysis_windows`: id, run_id FK, idx, first/core_first/core_last/last (ordinal), state (pending/running/succeeded/failed/unknown_outcome/cancelled), attempts, repair_used, error_code, result_json (перевірені кандидати вікна). `analysis_attempts`: id, window_id FK, kind (first/repair), request_id, spend_entry_id, state, http_status, error_code, raw_output (TEXT ≤ 1 МіБ, локальна діагностика без ключа), usage_json, created_at. `clips`: + evidence_start_ms/evidence_end_ms (обидва NULL або 0 ≤ start < end), FK analysis_run_id → analysis_runs.id.

§9 Завдання `analysis`. Create одною транзакцією пише run, вікна й job. Окремий робочий потік; вікна виконуються послідовно. Повтори 429/5xx/обрив до надсилання — як у STT (3 спроби, backoff, Retry-After ≤ 300 с). Таймаут після надсилання → вікно unknown_outcome, job failed ANALYSIS_UNKNOWN_OUTCOME; resume лише з `retry_unknown: true`. Інші коди: ANALYSIS_AUTH (401/403), ANALYSIS_FUNDS (402), ANALYSIS_REQUEST_REJECTED (400/404/422, зокрема немає провайдера зі structured outputs), ANALYSIS_UPSTREAM (повтори вичерпано), BUDGET_EXCEEDED (resume з `budget_usd`). Після успіху всіх вікон одна транзакція: §6 → §7 → кліпи `suggested` (analysis_run_id, recommended, evidence interval, categories, evidence_ids, reason, scores, rank, visual flag, evidence_type transcript) + run completed + diagnostics. Approved/rejected/manual кліпи не змінюються. Cancel, interrupted після перезапуску і resume — як у STT (ADR 032/035). Resume вікна failed — явна платна дія користувача: вікно починає спочатку, з новою repair-спробою.

§10 API. POST /v1/analysis-runs {source_id, transcript_id, profile, model?, budget_usd?} → 202 {id, job_id, status}. Порядок перевірок: 422 (тіло, profile — `details.field` = `profile.<поле>`, model, бюджет) → 404 SOURCE_NOT_FOUND → 404 TRANSCRIPT_NOT_FOUND → 422 TRANSCRIPT_SOURCE_MISMATCH → 409 TRANSCRIPT_REVISION_STALE {latest_id} (FR-012) → 409 TRANSCRIPT_PARTIAL (coverage не повна, а allow_partial false) → 409 API_KEY_REQUIRED (production) → 503 SERVICE_STOPPING → 409 ANALYSIS_RUN_ACTIVE {run_id, job_id}. POST /v1/analysis-runs/estimate (те саме тіло, бюджет необов'язковий) → {model, unit_level, unit_count, window_count, estimate_micro_usd (сума перших резервів), prompt_usd_per_mtok, completion_usd_per_mtok, max_tokens, price_basis, budget_usd|null, within_budget|null}. Нічого не пише й не шле. GET /v1/analysis-runs/{id} → run + {job_id, committed_micro_usd, windows {total, succeeded, failed, unknown_outcome, pending}, clip_ids (у порядку §7), stale, diagnostics_summary (кількості за причинами)}. GET /v1/analysis-runs?source_id= → {items}, новіші перші. Профіль — domain/search_profile.py: точні 6 ключів; categories 1–5 унікальні; custom_instruction ≤ 2000 кодових точок без Cs/NUL, зберігається як введено і передається лише як дані; тривалості 5000–600000, min ≤ max; max_candidates 1–100; allow_partial bool; канонічний порядок категорій.

§11 FR-020. Застарілість похідна: ClipOut отримує `analysis_stale`, а GET run — `stale` (те саме правило для run) = кліп має analysis_run_id, а ревізія його run не найновіша ревізія джерела. Виправлення транскрипту нічого не переписує в кліпах; ручні межі не змінюються.

§12 Desktop (Д-задачі). Панель «Що шукати» за docs/03 §6–7 і test id E2E-04. Перед платним запуском показується підсумок з estimate. Без ключа — «Відкрити Налаштування». Без перевіреної моделі — причина. Є прогрес, «Скасувати»/«Продовжити». У M4 кнопка «Знайти моменти» вимагає наявного транскрипту; ланцюг STT→аналіз однією кнопкою — у M5.

§13 Обмеження. Якість відбору fake не доводить (docs/06 §8). Live probe і вибір моделі за замовчуванням робить власник (NOT RUN). (Уточнено §24: probe виконано 2026-11-17; модель за замовчуванням не вшивається.) Кеш однакових запитів аналізу не робиться.

§14 Доповнення за Т5/Т6b (2026-11-17). Стани `analysis_attempts` — ті самі, що в вікна (pending/running/succeeded/failed/unknown_outcome/cancelled). Downgrade r0007 обнуляє `clips.analysis_run_id` і видаляє таблиці аналізу разом з даними, інакше повторний upgrade не пройде перевірку FK. `analysis_windows` має UNIQUE(run_id, idx), а CHECK `raw_output` рахує байти (`length(CAST(raw_output AS BLOB)) <= 1048576`) — Т5b. FK для `spend_entry_id` немає: ledger без FK, як у STT. HTTP-клієнт чату: одна спроба на виклик `complete` (повтори — у сервісі, §9). 413 → `invalid_request` (окремого payload_too_large для чату немає: вікно обмежене байтами, §3). Тіло надсилається тими самими компактними UTF-8 байтами, які рахує резерв. Таймаути — як у STT. Помилка після 200 (бите тіло) не несе cost, тож сервіс фіксує повний резерв як фактичну суму (§2).

§15 Уточнення за рев'ю Т1–Т6a (2026-11-17). `plan_windows` повертає позиції в списку одиниць, а `analysis_windows` і `validate_candidates` працюють з ordinal: сервіс переводить позиції в ordinal під час запису вікон і назад під час виконання (ordinal зростають, але можуть мати пропуски, ADR 027). Ліміт вікна max_window_bytes = min(98304, context_tokens − max_tokens − 4096) (замінено §16), менше 32768 → модель не підтримується; рівень одиниць обирає сервіс. Оцінки моделі — лише JSON-цілі без дробової частини (2.0 відхиляється, як у transcript_import), свідомо суворіше за JSON Schema. Title і reason з одних пробілів відхиляються (docs/06 §4). Наявний кліп у дедуплікації порівнюється за поточними start_ms/end_ms (з ручними межами); його evidence_ids порівнювані лише тоді, коли його run має той самий transcript_id і unit_level, інакше `None`. Повні дані suppressed і відкинутих кандидатів пише агрегатор у diagnostics (домен повертає ключі). Тип `max_price` (рядок чи число) перевіряє live probe Т10; до того надсилаються рядки.

§16 Ліміт вікна за контекстом моделі та рішення Т7a (2026-11-17). Формула §15 рахувала лише байти одиниць: системний промпт, схема, `custom_instruction` (до ≈8 КБ UTF-8) і repair-доповнення в ліміт не входили, тож запит міг перевищити контекст. Нова формула: max_window_bytes = min(98304, context_tokens − 2 × max_tokens − envelope_bytes). `envelope_bytes` — байти за формулою резерву §2 (messages + компактний `response_format` + 512) для більшого з двох запитів цього run з порожнім `units`: SELECT або REPAIR із 50 помилками максимальної довжини та порожнім `previous_output`. `previous_output` — власна відповідь моделі, обмежена max_tokens, тому на неї відводиться другий max_tokens; обрізання її лише скорочує. Байти правлять за верхню межу токенів, як і в резерві; спецтокени шаблону покривають 512 байт. Кожен рядок `validation_errors` обрізається до 256 байт UTF-8 на межі символу. Ліміт залежить від `custom_instruction`, тому рахується для кожного run у `plan_run`; менше 32768 → 422 ANALYSIS_MODEL_NOT_SUPPORTED (field `model`, текст радить іншу модель або коротшу інструкцію). Рішення Т7a: невідомий transcript_id → 404 TRANSCRIPT_NOT_FOUND; порожній транскрипт має unit_level `word`; `price_snapshot_json` = {prompt_usd_per_mtok, completion_usd_per_mtok (рядки, як надсилаються), max_tokens, price_basis}; непарні сурогати в `previous_output` перед обрізанням замінюються на U+FFFD (у них немає форми UTF-8).

§17 Агрегація (Т7c) і правила рушія (Т7b) (2026-11-17). `result_json` вікна — масив записів {status: accepted, index, candidate з evidence [[id, start_ms, end_ms]…], evidence_start_ms, evidence_end_ms} і {status: dropped, index, reason, candidate — сирий кандидат повністю}; вікно з жорсткими помилками не зберігається. `diagnostics_json` run = {dropped, rejected (з rank і кодом), suppressed (з rank, recommended і duplicate_of {kind: clip, id} або {kind: candidate, window_idx, index})}. `aggregate_run` відмовляє, якщо run уже completed або хоч одне вікно не succeeded: частковий результат не стає completed. Злиття дубля в межах run (§7) додає evidence, що лежить у recommended-інтервалі прийнятого, тому evidence-інтервал кліпу = від найменшого до найбільшого з (власний evidence-інтервал кандидата ∪ усі злиті evidence-записи) — кожен evidence id кліпу лежить у ньому (Т7c-2). Рушій: один рядок `analysis_attempts` на кожен HTTP-запит; перед кожним резервом committed + резерв > бюджет → BUDGET_EXCEEDED без надсилання, вікно лишається pending; ChatResult без cost → фактичною сумою фіксується повний резерв; `invalid_response` (бите тіло після 200) оплачується повним резервом і рахується як невалідна відповідь: витрачає repair-спробу з помилкою «provider response is not readable» і порожнім previous_output; `not_sent` звільняє резерв; `unknown_outcome` позначає запис ledger unknown; `model_unavailable` → ANALYSIS_REQUEST_REJECTED.

§18 Repair-запит у межах контексту (2026-11-17, за звітом Т7a-2). Конверт §16 рахував рядки помилок і `previous_output` як сирі байти, але в компактному JSON лапки, зворотні слеші й керівні символи займають 2–6 байт, а екранування додає токени. Тому: (1) кожен рядок `validation_errors` обрізається на межі символу так, щоб його JSON-форма (без лапок) мала ≤ 256 байт — тоді конверт §16 з 50 рядками по 256 ASCII-байт є точною верхньою межею; (2) repair-тіло будує сервісна функція `repair_body`, яка обрізає `previous_output` (після заміни сурогатів на U+FFFD) на межі символу так, щоб його JSON-форма мала ≤ min(65536, context_tokens − max_tokens − request_bytes(того самого тіла з порожнім previous_output)) байт. Формула §16 гарантує, що цей залишок ≥ max_tokens. Інваріант, що перевіряється тестом: request_bytes(будь-якого запиту run) + max_tokens ≤ context_tokens. Окрема одиниця, більша за ліміт вікна (ризик із Т7a-2), недосяжна: текст одиниці ≤ 2000 символів (transcript_import, transcript_merge), тобто < 32768 байт навіть з екрануванням. Т7a-2: ліміт рахується після читання ревізії, тож невідомий transcript_id дає 404 раніше за 422 моделі.
Уточнення §14 (за звітом Т7a-3): резерв і ліміти рахують байти UTF-8 текстів `content` повідомлень, які провайдер токенізує, плюс компактний `response_format`; HTTP-тіло більше на екранування цих текстів усередині JSON-тіла (лапки в user-JSON стають `\"`). Ліміт контексту від цього не залежить; «ті самі байти» в §14 означає, що надсилається саме те компактне тіло, яке побудував `build_chat_body`.

§19 Рушій run (Т7b, 2026-11-17). Вікно `unknown_outcome` не зупиняє run: решта вікон надсилаються, неоднозначне повторно не шлеться без `retry_unknown`. ANALYSIS_AUTH, ANALYSIS_FUNDS і BUDGET_EXCEEDED зупиняють run, ненадіслані вікна лишаються pending; скасування користувачем позначає ненадіслані вікна cancelled. Код run: код зупинки → скасування (status cancelled, без коду) → ANALYSIS_UNKNOWN_OUTCOME, якщо є unknown-вікно → код першого failed-вікна. Рядок `analysis_attempts` пишеться після резерву й безпосередньо перед HTTP-запитом; резерв без рядка спроби під час відновлення звільняється (не надсилався). Повторний `run()` для completed run → 409 ANALYSIS_RUN_COMPLETED; невідомий run → 404 ANALYSIS_RUN_NOT_FOUND; інший профіль/ціни → 409 RUN_OPTIONS_MISMATCH (уточнено §22); неправильний бюджет → 422 INVALID_BUDGET (назви як у STT). Захист від паралельного запуску на рівні run_id; 409 ANALYSIS_RUN_ACTIVE {run_id, job_id} на рівні джерела — у шарі job/API. Повтори й cooldown 429 спільні з STT (`backoff_seconds`, `cancellable_sleep`, MAX_RETRY_AFTER_S); cooldown 429 діє на всі run сервісу. Вікна виконуються послідовно в робочому потоці.

§20 Шар завдань analysis (Т7d, 2026-11-17). Порядок перевірок create: 422 тіла (profile, model — з запиту або `analysis_model` налаштувань, ANALYSIS_MODEL_REQUIRED коли немає; budget_usd — правило налаштувань, BUDGET_REQUIRED коли немає) → 404 SOURCE_NOT_FOUND → 404 TRANSCRIPT_NOT_FOUND → 422 TRANSCRIPT_SOURCE_MISMATCH → 422 ANALYSIS_MODEL_NOT_SUPPORTED (ліміт вікна потребує транскрипту, тому після 404) → 409 TRANSCRIPT_REVISION_STALE {latest_id} (повторно під write lock) → 409 TRANSCRIPT_PARTIAL (хоч один coverage-запис не succeeded, а allow_partial false) → 409 API_KEY_REQUIRED (production) → під замком admission 503 SERVICE_STOPPING → 409 ANALYSIS_RUN_ACTIVE {run_id, job_id} (job джерела queued/running/cancelling). Estimate застосовує лише 422/404/422 (без stale, partial і ключа) і нічого не пише. Resume: 422 бюджету → 503 SERVICE_STOPPING → 404/409 JOB_NOT_RESUMABLE → 409 ANALYSIS_RUN_ACTIVE → 409 UNKNOWN_OUTCOME_REQUIRES_DECISION {count} → 409 API_KEY_REQUIRED, як у STT (ADR 035). Checkpoint = {run_id, budget_usd} (+ `error` після провалу, як у services/jobs.py); ключ читає `KeyedChatClient` у момент запиту. Стан job: completed → succeeded, cancelled → cancelled, failed → failed з кодом run, зупинка shutdown → interrupted. `windows.pending` у GET run = total − succeeded − failed − unknown_outcome (включає running і cancelled). `clip_ids` GET run — у порядку вставки агрегатором (SQLite rowid, ризик у known-issues). Числовий budget_usd приймається і зберігається як рядок (§2).

§21 Desktop IPC (Д1, 2026-11-17). Нові ops `analysis.estimate` і `analysis.create` мають params {source_id, transcript_id, profile}. Model і budget_usd до params не входять: backend бере їх із налаштувань, як у STT (ADR 038), тому запуск завжди відповідає екрану Налаштувань. Для `analysis.create` можна змінити бюджет пізніше, через `jobs.resume` {budget_usd}. Main перевіряє форму профілю: рівно 6 ключів, categories — масив рядків, custom_instruction — рядок, min/max_duration_ms і max_candidates — цілі, allow_partial — bool. Значення й межі перевіряє backend (422 з `details.field`). `analysis.get` має params {id}, `analysis.list` — {source_id}. Скасування й продовження йдуть через наявні `jobs.*`. Парсер ClipDto вимагає поле `analysis_stale: boolean`.

§22 Рішення за рев'ю бекенду M4 (2026-11-17).
(1) HTTP 408 і 504 після надсилання дають неоднозначний результат: провайдер міг обробити запит і виставити рахунок. Тому і чат, і STT повертають на них `unknown_outcome`: повтор лише з `retry_unknown` (інваріант CLAUDE.md). 500, 502 і 503 лишаються `upstream` з повторами за §9. Для STT це змінює поведінку M3.
(2) RUN_OPTIONS_MISMATCH відповідає 409, як у STT; цей код бачить лише worker. Порівнюються model, price_snapshot, профіль, prompt_version і schema_version: run не продовжується під іншим промптом зі старою позначкою.
(3) §2: bool у `budget_usd` дає 422 INVALID_RUN_BUDGET і в HTTP API. Поле запиту приймає будь-який JSON, перевірку робить сервіс.
(4) §17: на кожного кандидата пишеться один dropped-запис. Якщо причин дві, `reason` = NOT_OWNED: кандидат належить іншому вікну.
(5) Т3c: `plan_windows` кидає ValueError, коли context_max_bytes < 0, коли 2·context_max_bytes ≥ max_window_bytes і коли ordinal не зростають. `validate_candidates` кидає ValueError на дубль id одиниці. Це помилки програміста, а не коди для користувача.
(6) Коди ANALYSIS_UPSTREAM, ANALYSIS_REQUEST_REJECTED і ANALYSIS_INVALID_OUTPUT отримують окремі тексти job з дієвою порадою.
(7) Відновлення після аварії (рев'ю Т10–Т11, medium). Вікно `running` без живої спроби класифікується за своєю останньою спробою, тим самим правилом, що й жива: запис ledger є і не released (reserved, completed, unknown) → вікно unknown_outcome (термінальний стан самої спроби не змінюється); спроби немає або запис released → pending. Без цього аварія між оплаченою відповіддю й записом вікна робила вікно pending, і resume платив за нього вдруге без рішення користувача. Повторна перевірка збереженого raw_output без запиту відкладена (known-issues). Уточнення до (2): профіль порівнюється лише тоді, коли виклик його передає; resume бере профіль із самого run, тому для resume це порівняння тотожне.
Відкладено в known-issues: повторна оплата першої відповіді, коли бюджет закінчився на repair; `create_run` використовується лише в тестах; статус 1xx/204/3xx оплачується повним резервом.
